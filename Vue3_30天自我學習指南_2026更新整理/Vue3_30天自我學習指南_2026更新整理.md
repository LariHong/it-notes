## 主線專案

### 專案最終會長成什麼

全系列用一個 2026 補強主線專案 `vue-product-workbench` 串起 30 天。這不是原文宣稱的專案，而是為了讓學習者把每一天概念放進真實工作流程。

最後會做出一個簡化的商品管理工作台：

- `ProductListView` 顯示商品列表、篩選、排序與 empty 狀態。

### 在 VS Code 裡正常做 Vue 專案的方式

初學範例常把所有東西放在單一 `.vue` 檔，這樣方便解釋語法，但真實 Vue 專案通常不是這樣長期維護。Vue 的核心精神是「由很多 component 組合成頁面」，再把可重用邏輯抽到 composable，把跨頁狀態放到 store，把 API 細節放到 service。

2026 年一般 Vue 3 專案在 VS Code 內建議這樣準備：

1. 安裝 VS Code 擴充 `Vue - Official`，也就是以前常聽到的 Volar。Vue 官方工具文件建議 VS Code 搭配 `Vue - Official`，它提供 Vue SFC 語法、TypeScript、template props / emits / slots 的提示與型別檢查。
2. 如果專案是 Vue 3，避免同時啟用舊的 `Vetur`。Vetur 主要是 Vue 2 時代的擴充，和 Vue 3 / `<script setup>` 專案容易打架。
3. 用 Vite 建立專案，平常在 VS Code 終端機跑 `npm run dev`，瀏覽器看畫面，VS Code 負責編輯與型別提示。
4. `.vue` 檔案通常是「一個元件一個檔案」。不要把整個產品頁、表格、表單、API request、搜尋邏輯全部塞進同一個檔案。
5. 開發時常用 VS Code 左側 Explorer 建檔，並搭配 `Ctrl+P` 快速開檔、`F2` rename symbol、右鍵 rename file 或移動檔案。元件命名通常用 PascalCase，例如 `ProductForm.vue`。

常見專案資料夾會長這樣：

```text
src/
  main.ts
  App.vue
  router/
    index.ts
  views/
    ProductListView.vue
    ProductEditorView.vue
    ProductDetailView.vue
  components/
    ProductTable.vue
    ProductForm.vue
    ProductRow.vue
    BaseButton.vue
    ErrorBoundary.vue
  composables/
    useProductSearch.ts
    useDebouncedRef.ts
    usePagination.ts
  stores/
    productStore.ts
  services/
    productApi.ts
  types/
    product.ts
```

這些資料夾的直覺分工：

| 資料夾 | 正常放什麼 | 不建議放什麼 |
| --- | --- | --- |
| `views/` | 路由頁面，負責組合元件與流程 | 可重用小元件細節 |
| `components/` | 可重用 UI 元件，例如表格、表單、卡片 | API request 與跨頁狀態 |
| `composables/` | 可重用狀態邏輯，例如搜尋、分頁、debounce | template 或 CSS |
| `stores/` | Pinia 跨頁狀態，例如商品列表、登入使用者 | 單一 input 的局部狀態 |
| `services/` | API 呼叫、DTO mapping、錯誤轉換 | 畫面顯示邏輯 |
| `types/` | TypeScript 型別 | 實際執行的業務流程 |

以商品列表頁為例，正常不是寫成一個超大的 `ProductListView.vue`，而是這樣組合：

```vue
<!-- src/views/ProductListView.vue -->
<script setup lang="ts">
// 範例用途：路由頁面負責組合 store、composable 與 components。
// 輸入：使用者在搜尋框輸入 keyword。
// 輸出：畫面顯示商品列表、loading、empty、error 狀態。
import ProductTable from '@/components/ProductTable.vue'
import { useProductSearch } from '@/composables/useProductSearch'

const { keyword, results, loading, error, search } = useProductSearch()
</script>

<template>
  <main>
    <input v-model="keyword" @keyup.enter="search" placeholder="搜尋商品" />

    <p v-if="loading">載入中...</p>
    <p v-else-if="error">{{ error }}</p>

    <ProductTable v-else :products="results">
      <template #actions="{ product }">
        <RouterLink :to="`/products/${product.id}/edit`">編輯</RouterLink>
      </template>
    </ProductTable>
  </main>
</template>
```

這個頁面看起來仍然是一個頁面，但它不自己做所有事：

- `ProductListView.vue`：接使用者操作、組合流程。
- `ProductTable.vue`：只負責把商品資料畫成表格。
- `useProductSearch.ts`：只負責搜尋狀態與搜尋動作。
- `productApi.ts`：只負責 HTTP request 與 response mapping。

所以，單頁式範例可以用來理解語法；一旦進到工作專案，就要慢慢拆成「頁面組合元件、元件呈現 UI、composable 管邏輯、store 管跨頁資料、service 管 API」。後面 Day 13 到 Day 16 的 props、emits、slot、無渲染元件，就是在教這種 component 組合能力。

### 主線端到端流程

1. 使用者進入 `/products`。
2. Router 載入 `ProductListView`。
3. 頁面呼叫 Pinia store 的 `loadProducts()`。
4. Store 呼叫 `productApi.list()`。
5. API service 轉換 response 為前端 `Product`。
6. 頁面用 computed 產生排序、篩選後的列表。
7. `ProductTable` 用 props 接資料，用 slot 讓父層客製操作欄。
8. 使用者點編輯，Router 進入 `/products/:id/edit`。
9. `ProductEditorView` 建立表單草稿，送出後呼叫 store 儲存。
10. 成功時回列表，失敗時顯示錯誤並保留草稿。

## Day 1：Vue Create App and Mount

### 這篇文章主要在講什麼

這篇建立 Vue app 的第一個直覺：`createApp()` 不是把整個瀏覽器變成 Vue，而是建立一個 Vue 應用實例；`mount()` 是把這個應用掛到 HTML 裡的某個 DOM 容器。

### 為什麼需要這個概念

如果你不知道 app 從哪裡開始，後面看到 router、Pinia、plugin、全域錯誤處理都會覺得它們憑空出現。真實專案中，很多 bug 其實是入口註冊順序、mount 位置或插件漏裝造成。

### 學完這篇你應該會做到什麼

- 找到 Vue 專案入口 `src/main.ts`。
- 知道 `index.html` 的 `#app` 與 `mount('#app')` 如何對上。
- 能判斷 plugin 應該在 mount 前註冊。

### 核心重點

- `createApp(App)` 建立應用實例。
- `app.use(router)`、`app.use(pinia)` 要在 `mount()` 前。
- DOM 相關操作不要放在 `main.ts` 硬查元素，應放在元件生命週期。

### 知識點補充

- [createApp()](Vue3_30天自我學習指南_2026更新整理知識點補充.md#createapp)
- [mount()](Vue3_30天自我學習指南_2026更新整理知識點補充.md#mount)

### 真實工作流程例子

- 工作任務：新專案要接商品管理頁，PM 說「先讓商品列表頁跑起來，後面再接 API」。
- 你先判斷：先確認 app 入口和頁面掛載，不急著寫商品邏輯；如果入口沒跑通，後面元件都不會出現。
- 會動到：`index.html`、`src/main.ts`、`src/App.vue`、`src/views/ProductListView.vue`。
- 資料怎麼流：瀏覽器讀 `index.html` -> `main.ts` 建立 app -> `App.vue` 顯示 route 或頁面 -> `ProductListView` 顯示初始內容。
- 流程路線圖：需求 -> `index.html #app` -> `main.ts createApp` -> `App.vue` -> `ProductListView` -> 畫面。
- 工作中會寫 / 檢查的片段：

```ts
// src/main.ts
// 範例用途：建立 Vue app 並掛到 index.html 的 #app。
// 輸入：App 根元件。
// 副作用：瀏覽器畫面開始由 Vue 接管。
import { createApp } from 'vue'
import App from './App.vue'

createApp(App).mount('#app')
```

- 交付前驗證：開瀏覽器確認頁面出現；把 `#app` 拼錯一次，確認錯誤來自 mount 目標。
- 常見卡點：畫面空白時先查 DevTools console，再查 `index.html` 是否真的有 `<div id="app"></div>`。

### 主線專案銜接

今天接到主線的 app 啟動點。

1. 建立 `vue-product-workbench`。
2. 確認 `src/main.ts` 能掛載 `App.vue`。
3. 在 `App.vue` 暫時放入 `ProductListView`。

檢查項目：畫面有標題；console 無 mount 錯誤；`main.ts` 沒有把 plugin 放在 mount 後。

### 當天做完後檢查

- `npm run dev` 成功。
- 瀏覽器看到 Vue 畫面。
- 修改 `App.vue` 文字會熱更新。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| HTML 容器 | `index.html` | 提供 `#app` |
| App 入口 | `src/main.ts` | 建立與 mount Vue app |
| 根元件 | `src/App.vue` | 顯示第一個頁面 |

### 完整實作流程、範例與注意事項

1. 用 Vite 建立 Vue 專案。
2. 開啟 `index.html` 確認有 `id="app"`。
3. 在 `main.ts` 使用 `createApp(App).mount('#app')`。
4. 啟動 dev server。
5. 修改 `App.vue` 驗證畫面更新。

注意事項：不要在 `main.ts` 中直接寫大量業務邏輯；入口只負責組裝 app。

### 如果結果和預期不同

- 空白頁：先查 console 是否有 selector 找不到。
- 熱更新無效：確認 dev server 沒停。
- 元件沒顯示：確認 `App.vue` 有被 import。

### 負面例子 / 錯誤用法

錯誤做法：在 `main.ts` 裡直接查 DOM、綁事件、塞商品資料。

問題：入口會變成雜物間，測試與維護困難。

修正方向：入口只註冊 app；商品資料放 store 或 page。

### 小練習

把 `App.vue` 改成顯示「商品管理工作台」，再新增 `ProductListView.vue` 並引入。

### Junior 常見誤解

以為 `mount()` 是每個元件都要呼叫。實際上通常整個 SPA 只在入口 mount 一次。

### 一句話總結

Vue app 的第一步是建立應用實例，再把它掛到 HTML 容器。

## Day 2：Vue SFC Template 和 Render Function

### 這篇文章主要在講什麼

這篇說明 `.vue` 單檔元件的 `<template>` 最後會被編譯成 render function。template 是比較適合團隊閱讀的寫法；render function 是更接近底層 VNode 的寫法。

### 為什麼需要這個概念

你不一定每天寫 render function，但你需要知道 template 不是魔法。這能幫你理解為什麼某些動態 UI、欄位渲染器、元件庫會改用 render function 或 JSX。

### 學完這篇你應該會做到什麼

- 知道 template 與 render function 都是在描述 UI。
- 判斷一般業務畫面優先用 template。
- 看懂元件庫中 `h()` 的基本意思。

### 核心重點

- template 可讀性高，適合多數 Vue 專案。
- render function 適合高度動態 UI。
- 不要為了炫技把普通頁面改成 render function。

### 真實工作流程例子

- 工作任務：後台表格需要讓不同欄位用不同方式顯示，像價格欄、狀態欄、操作欄。
- 你先判斷：一般列表頁用 template；如果欄位配置來自 schema，才考慮 render function 或 slot。
- 會動到：`ProductTable.vue`、`columns.ts`、父層 `ProductListView.vue`。
- 資料怎麼流：父層傳 products 與 columns -> table 迭代欄位 -> template 或 render function 產生 cell。
- 流程路線圖：需求 -> 欄位 schema -> `ProductTable` -> cell renderer -> 表格畫面。
- 工作中會寫 / 檢查的片段：

```ts
// columns.ts
```

## Day 3：`<script setup>` 語法糖的本質

### 這篇文章主要在講什麼

這篇說明 `<script setup>` 是 Composition API 的編譯期語法糖。它讓你不用手動 `return` 給 template，也讓 props、emits、model 這些元件 API 更集中。

## Day 4：JavaScript 物件常見操作方法

### 這篇文章主要在講什麼

這篇整理物件操作，例如展開、解構、複製與參考。Vue 的資料狀態底層仍是 JavaScript 物件；如果不了解參考與複製，就很容易誤改原資料。

### 為什麼需要這個概念

表單編輯最常見的 bug 是「還沒按儲存，列表資料已經變了」。原因通常是表單草稿直接引用原物件，而不是建立可控的 copy。

### 學完這篇你應該會做到什麼

- 分辨淺拷貝與深拷貝。
- 為表單建立 draft。
- 知道解構 reactive 物件會影響響應式連結。

### 核心重點

- 物件是參考型別。
- `{ ...product }` 是淺拷貝。
- 深層資料要評估 `structuredClone()` 或明確 mapping。

### 真實工作流程例子

- 工作任務：QA 回報「編輯商品但按取消，列表價格還是被改掉」。
- 你先判斷：這不是 API 問題，先查表單是否直接修改列表 row。
- 會動到：`ProductEditorView.vue`、`types/product.ts`。
- 資料怎麼流：列表 row -> 編輯頁建立 draft -> 使用者修改 draft -> 儲存才寫回 store。
- 流程路線圖：QA bug -> list row -> editor draft -> submit -> store update -> list refresh。
- 工作中會寫 / 檢查的片段：

```ts
// 範例用途：建立表單草稿，避免直接改原始商品。
// 輸入：從 store 取得的 product。
// 回傳：可安全編輯的 draft。
function createProductDraft(product: Product): ProductDraft {
  return structuredClone({
    id: product.id,
    name: product.name,
    price: product.price,
    tags: product.tags,
  })
}
```

- 交付前驗證：按取消列表不變；按儲存列表才更新。
- 常見卡點：只用展開複製第一層，但 `tags` 這種陣列仍共用。

### 主線專案銜接

今天建立商品編輯草稿流程。

1. 從 store 取商品。
2. 建立 draft。
3. 儲存才呼叫 store update。

檢查項目：取消不改原資料；深層陣列不共用；提交 payload 清楚。

### 當天做完後檢查

- 編輯時列表資料不會即時被污染。
- submit payload 是 draft。
- console 不出現 proxy 混用錯誤。

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 資料型別 | `types/product.ts` | 定義 Product / ProductDraft |
| 編輯頁 | `ProductEditorView.vue` | 建立 draft |
| Store | `productStore.ts` | 儲存更新 |

### 完整實作流程、範例與注意事項

1. 定義 `ProductDraft`。
2. 進入編輯頁時建立 draft。

4. 按取消丟棄 draft。
5. 按儲存送出 draft。

### 如果結果和預期不同

錯誤做法：`const draft = selectedProduct`。

問題：draft 和原資料是同一個物件。

修正方向：建立 copy，儲存成功才合併。

### 小練習

### Junior 常見誤解

以為 `const` 代表物件不能被改。`const` 只代表變數不能重新指向，不代表物件內容不能改。

## Day 5：JavaScript Proxy 和 Vue Reactive 響應式系統

### 這篇文章主要在講什麼

這篇解釋 Vue 3 的 `reactive()` 如何透過 Proxy 攔截物件讀寫，讓 Vue 知道哪些資料被讀取、哪些資料變更後要更新畫面。

### 為什麼需要這個概念

你不需要自己實作 Vue reactivity，但你要知道 Vue 是透過「讀取追蹤、寫入觸發」來更新畫面。這能幫你排查「為什麼畫面沒更新」或「為什麼更新太多次」。

### 學完這篇你應該會做到什麼

- 知道 `reactive()` 適合物件。
- 知道不要混用 raw object 和 proxy。
- 能分辨資料變更是否被 Vue 追蹤。

### 核心重點

- Proxy 攔截 get/set。
- Vue 追蹤 reactive 狀態的讀取依賴。
- 更新 reactive 狀態會觸發相關畫面重新計算。

### 真實工作流程例子

- 工作任務：QA 說「商品價格改了，但總價沒有更新」。
- 你先判斷：先查總價是否依賴 reactive 狀態，而不是查 CSS 或 API。
- 會動到：`productStore.ts`、`ProductListView.vue`。
- 資料怎麼流：store reactive products -> computed totalPrice -> template 顯示。
- 流程路線圖：bug -> store state -> computed dependency -> template -> Devtools 檢查。
- 工作中會寫 / 檢查的片段：

```ts
// productStore.ts
// 範例用途：用 reactive state 保存商品列表。
// 輸入：API 回來的 products。
// 副作用：products 改變時，依賴它的 computed / template 會更新。
const state = reactive({
  products: [] as Product[],
})
```

- 交付前驗證：修改 price 後總價更新；Devtools 能看到 state 變化。
- 常見卡點：把 reactive 物件解構後傳出去，導致依賴不如預期。

### 主線專案銜接

今天讓商品列表成為 reactive 狀態。

1. 建立 reactive state。
2. 將列表畫面依賴 state。
3. 透過按鈕修改 price 測試更新。

檢查項目：畫面更新；computed 更新；沒有直接操作 DOM。

### 當天做完後檢查

- state 改變後畫面同步。
- Devtools 可觀察 products。
- 不混用 raw 與 proxy 做比較。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 狀態 | `productStore.ts` | 保存 reactive products |
| 頁面 | `ProductListView.vue` | 讀取狀態 |
| 顯示 | template | 根據狀態更新 |

### 完整實作流程、範例與注意事項

1. 建立 reactive products。
2. 在 template 迭代顯示。
3. 新增修改商品價格的操作。
4. 觀察畫面是否更新。
5. 用 Devtools 確認 state。

注意事項：`reactive` 不是資料庫，也不是 API cache；它只是前端狀態追蹤。

### 如果結果和預期不同

- 畫面不更新：檢查是否改到非 reactive 來源。
- 比較失敗：檢查是否拿 proxy 和 raw object 比。
- 更新太多：檢查 computed 或 watcher 是否依賴太廣。

### 負面例子 / 錯誤用法

錯誤做法：把 reactive 物件整個解構成普通變數後期待保持響應式。

問題：可能失去追蹤或造成可讀性混亂。

修正方向：保留物件，或使用 `toRefs()`。

### 小練習

### Junior 常見誤解

以為 Vue 每秒掃描資料變了沒。實際上 Vue 是透過依賴追蹤知道誰該更新。

### 一句話總結

Vue 3 的響應式核心是 Proxy 追蹤讀取與觸發更新。

## Day 6：Vue 的響應式系統 Ref

### 這篇文章主要在講什麼

這篇說明 `ref()` 是包住單一值的響應式容器。script 中用 `.value`，template 會自動解包。

### 為什麼需要這個概念

表單欄位、loading、error、DOM ref、目前選取 id 這類單一值很常用 `ref()`。如果不懂 `.value`，你會在 script 裡一直拿錯值。

### 學完這篇你應該會做到什麼

- 用 ref 管理 primitive state。
- 用 template ref 操作 DOM focus。
- 知道 ref 在 template 與 script 的差異。

### 核心重點

- `const keyword = ref('')`。
- script 裡讀寫 `keyword.value`。
- template 裡直接用 `keyword`。

### 真實工作流程例子

- 工作任務：PM 要求新增商品後自動 focus 到商品名稱欄位。
- 你先判斷：這是 DOM 操作時機問題，用 template ref 與 `onMounted`，不是用 querySelector 到處找。
- 會動到：`ProductEditorView.vue`。
- 資料怎麼流：頁面 mount -> input DOM ref 可用 -> focus。
- 流程路線圖：需求 -> template ref -> `onMounted` -> input focus -> 使用者輸入。
- 工作中會寫 / 檢查的片段：

```vue
<script setup lang="ts">
// 範例用途：頁面載入後 focus 商品名稱 input。
// 輸入：template 內 ref="nameInput" 的 DOM。
// 副作用：游標進入 input。
const nameInput = ref<HTMLInputElement | null>(null)
onMounted(() => nameInput.value?.focus())
</script>

<template>
  <input ref="nameInput" />
</template>
```

- 交付前驗證：進入新增頁會 focus；重新整理後仍正常。
- 常見卡點：在 setup 立即讀 DOM，此時 DOM 還沒 mount。

### 主線專案銜接

今天處理表單欄位與 focus。

1. 用 ref 建立商品名稱。
2. 用 DOM ref 指向 input。
3. mount 後 focus。

檢查項目：`.value` 使用正確；DOM 可為 null；focus 不報錯。

### 當天做完後檢查

- input 預設 focus。
- 欄位輸入能更新 ref。
- TypeScript 能處理 null。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 狀態 ref | `ProductEditorView.vue` | 管理欄位值 |
| DOM ref | template input | 提供 focus 目標 |
| 生命週期 | `onMounted` | 等 DOM 建好再操作 |

### 完整實作流程、範例與注意事項

1. 建立 `const name = ref('')`。
2. 用 `v-model="name"` 綁 input。
3. 建立 `nameInput` DOM ref。
4. `onMounted` focus。
5. 測試新增與編輯頁。

注意事項：template ref 初始是 null，不要直接 `nameInput.value.focus()`。

### 如果結果和預期不同

- focus 沒反應：檢查 ref 名稱是否一致。
- TS 報 null：加 optional chaining。
- template 顯示 `[object Object]`：檢查是不是把 ref 物件直接傳到非 Vue 處理的位置。

### 負面例子 / 錯誤用法

錯誤做法：`document.querySelector('input')?.focus()`。

問題：元件重用、多 input 或 SSR 場景容易出錯。

修正方向：用 template ref 精準指向元件內元素。

### 小練習

新增 `price` 欄位，儲存失敗時 focus 到價格 input。

### Junior 常見誤解

以為 `.value` 在 template 也要寫。template 會自動解包，script 才需要 `.value`。

### 一句話總結

`ref()` 是 Vue 管理單一響應式值和 DOM 引用的基本工具。

## Day 7：Vue 的計算屬性 Computed

### 這篇文章主要在講什麼

這篇說明 `computed()` 用來定義由狀態推導出的值，例如篩選後列表、排序結果、總價、是否可送出。

### 為什麼需要這個概念

如果你把衍生資料都存成 state，很容易發生「來源改了，但衍生值忘記同步」。computed 讓你把資料關係寫清楚。

### 學完這篇你應該會做到什麼

- 用 computed 做篩選與總計。
- 避免把可以推導的值存成 state。
- 知道 computed 應保持純粹，不放副作用。

### 核心重點

- computed 有快取。
- 依賴變了才重新計算。
- 不要在 computed 裡打 API 或改 state。

### 真實工作流程例子

- 工作任務：商品列表需要依關鍵字篩選，並顯示篩選後總金額。

- 會動到：`ProductListView.vue`。
- 資料怎麼流：products + keyword -> computed filteredProducts -> computed totalPrice -> template。
- 流程路線圖：需求 -> state -> computed filter -> computed total -> 畫面。
- 工作中會寫 / 檢查的片段：

```ts
// 範例用途：依使用者輸入推導篩選後商品。
// 輸入：products 與 keyword。
// 回傳：畫面要顯示的商品清單。
const filteredProducts = computed(() =>
  products.value.filter(product => product.name.includes(keyword.value))

```

- 交付前驗證：改 keyword 會更新列表；清空 keyword 顯示全部。
- 常見卡點：在 computed 裡改 `keyword.value`，造成難追的循環。

### 主線專案銜接

今天完成列表篩選。

1. 建立 `keyword`。
2. 建立 `filteredProducts`。
3. 建立 `totalPrice`。

檢查項目：沒有多餘 state；computed 命名清楚；空資料狀態正常。

### 當天做完後檢查

- 搜尋能篩選。
- 總價跟著篩選變動。
- computed 沒有副作用。

### 範例範圍地圖

| 推導資料 | computed | 篩選與總計 |

### 完整實作流程、範例與注意事項

1. 新增 keyword input。

注意事項：computed 是「答案」，不是「動作」；動作用 method 或 watch。

### 如果結果和預期不同

## Day 8：Vue 的數據監聽器 watch 和 watchEffect

### 這篇文章主要在講什麼

這篇說明 `watch()` 和 `watchEffect()` 都能處理副作用，但適用情境不同。`watch()` 明確指定來源；`watchEffect()` 自動追蹤依賴。

### 為什麼需要這個概念

工作中常需要「某個資料變了就做事」，例如搜尋關鍵字改變後打 API、路由參數改變後重新載入資料。這些不是 computed，因為它們有副作用。

### 學完這篇你應該會做到什麼

- 用 watch 監聽明確來源。
- 知道 watchEffect 適合簡單自動追蹤。
- 不把 API call 放進 computed。

### 核心重點

- `watch(source, callback)` 可拿 newValue / oldValue。
- `watchEffect()` 會立即執行並自動追蹤。
- API、log、localStorage、request 都屬於副作用。

### 真實工作流程例子

- 工作任務：使用者輸入搜尋字時，自動更新商品查詢結果。
- 你先判斷：搜尋 request 是副作用，使用 watch；篩選本地陣列才用 computed。
- 會動到：`useProductSearch.ts`、`productApi.ts`。
- 資料怎麼流：keyword -> watch -> API request -> results -> view。
- 流程路線圖：輸入 -> keyword ref -> watch -> `productApi.search` -> results -> table。
- 工作中會寫 / 檢查的片段：

```ts
// 範例用途：keyword 改變時觸發搜尋。
// 輸入：使用者輸入的 keyword。
// 副作用：呼叫 API 並更新 results。
watch(keyword, async newKeyword => {
  results.value = await productApi.search(newKeyword)
})
```

- 交付前驗證：keyword 改變會發 request；空字串不打無意義 API。
- 常見卡點：watch 內沒有處理過期 request，快速輸入時結果順序可能錯。

### 主線專案銜接

今天建立搜尋副作用。

1. 建立 `keyword`。
2. 用 watch 呼叫 search API。
3. 把結果寫入 results。

檢查項目：不在 computed 打 API；空字串有處理；錯誤狀態有顯示。

### 當天做完後檢查

- 輸入會觸發查詢。
- 清空輸入回到預設列表。
- API 失敗時不白屏。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| composable | `useProductSearch.ts` | watch keyword |
| service | `productApi.ts` | 發 API |
| view | `ProductListView.vue` | 顯示結果 |

### 完整實作流程、範例與注意事項

1. 抽出 `useProductSearch`。
2. 在 composable 中宣告 keyword / results / loading。
3. watch keyword。
4. 呼叫 API。
5. 在 view 顯示 loading、results、error。

注意事項：watch 處理副作用；computed 處理推導資料。

### 如果結果和預期不同

- API 打太多：加 debounce。
- 舊結果覆蓋新結果：Day 12 補 cleanup。
- watch 沒執行：確認 source 是 ref 或 getter。

### 負面例子 / 錯誤用法

錯誤做法：在 computed 裡 `await productApi.search()`。

問題：computed 應該純粹，非同步副作用會讓資料流混亂。

修正方向：computed 只推導；watch 負責副作用。

### 小練習

加入 `watchEffect()` 顯示目前搜尋條件到 console，觀察它立即執行的特性。

### Junior 常見誤解

以為只要資料變了就一定用 watch。若只是畫面推導，computed 更適合。

### 一句話總結

## Day 9：Vue 監聽器的執行時機點

### 這篇文章主要在講什麼

這篇說明 watcher callback 的執行時機，特別是 DOM 更新前後。Vue 預設會批次更新畫面，因此 watch 不一定能立刻讀到最新 DOM。

### 為什麼需要這個概念

真實工作中常遇到「資料已經改了，但量到的高度還是舊的」。這不是 Vue 壞掉，而是你讀 DOM 的時機太早。

### 學完這篇你應該會做到什麼

- 知道 `flush: 'pre'`、`post`、`sync` 差異。
- 讀 DOM 時優先用 post timing。
- 避免 sync watch 造成效能問題。

### 核心重點

- 預設 watch 在元件 DOM 更新前執行。
- DOM 更新後讀取可用 `flush: 'post'`。
- `sync` 要非常小心。

### 真實工作流程例子

- 工作任務：搜尋結果更新後，要自動把結果區捲到第一筆。
- 你先判斷：這是 DOM 更新後操作，watch 要用 post 或 nextTick。
- 會動到：`ProductListView.vue`。
- 資料怎麼流：results 改變 -> DOM 重新渲染 -> watch post -> scroll。
- 流程路線圖：搜尋 -> results -> DOM 更新 -> post watcher -> scrollIntoView。
- 工作中會寫 / 檢查的片段：

```ts
// 範例用途：結果更新並渲染後，捲到結果區。
// 輸入：results 長度。
// 副作用：操作 DOM scroll。
watch(() => results.value.length, () => {
  resultPanel.value?.scrollIntoView({ behavior: 'smooth' })
}, { flush: 'post' })
```

- 交付前驗證：搜尋後會捲到結果；空結果不亂捲。
- 常見卡點：用預設 watch 讀高度，讀到舊值。

### 主線專案銜接

今天修正搜尋結果的 DOM 操作時機。

1. 建立 result panel ref。
2. watch results length。
3. 使用 post flush。

檢查項目：DOM ref 不為 null；空結果處理；不使用 sync。

### 當天做完後檢查

- 結果更新後才 scroll。
- 不會在初始載入就亂跳。
- 大量更新時不卡頓。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 結果資料 | `results` | 觸發畫面更新 |
| DOM ref | `resultPanel` | scroll 目標 |
| watcher | `ProductListView.vue` | 控制時機 |

### 完整實作流程、範例與注意事項

1. 在 template 加 `ref="resultPanel"`。
2. 在 script 建立 DOM ref。
3. watch results length。
4. 加上 `flush: 'post'`。
5. 測試有資料與空資料。

注意事項：讀 DOM 尺寸和位置時，先確認 DOM 已更新。

### 如果結果和預期不同

- scroll 沒發生：確認 ref 掛在正確元素。
- scroll 太早：確認有 `flush: 'post'`。
- 頁面抖動：加入條件避免無意義 scroll。

### 負面例子 / 錯誤用法

錯誤做法：watch 裡立即讀 `offsetHeight`，然後用舊高度計算。

問題：DOM 還沒更新，結果不準。

修正方向：用 post watch 或 `await nextTick()`。

### 小練習

搜尋後顯示結果數量，並在 DOM 更新後量測結果區高度。

### Junior 常見誤解

以為 state 改完 DOM 也立刻改完。Vue 會批次更新 DOM。

### 一句話總結

副作用若依賴最新 DOM，就要注意 watcher 的 flush timing。

## Day 10：JavaScript 事件循環、宏任務和微任務

### 這篇文章主要在講什麼

這篇用事件循環、macro task、micro task 來理解 Vue 為什麼會批次更新 DOM，以及 `nextTick()` 為什麼能等到 DOM 更新後。

### 為什麼需要這個概念

你會遇到「我已經改 state，為什麼 DOM 還沒變」這類問題。理解事件循環後，就知道這不是同步逐行立刻更新 DOM，而是排程。

### 學完這篇你應該會做到什麼

- 知道 Vue 更新是批次排程。
- 知道多次 state 修改會合併更新。
- 理解 `nextTick()` 的必要性。

### 核心重點

- JavaScript 主執行緒一次跑一段任務。
- Promise microtask 通常早於下一個 macrotask。
- Vue 用排程避免每次修改都重畫。

### 真實工作流程例子

- 工作任務：新增商品後，立刻讀列表最後一列文字卻讀不到。

- 流程路線圖：新增事件 -> state push -> render queue -> DOM patch -> nextTick callback。
- 工作中會寫 / 檢查的片段：

```ts
// 範例用途：新增商品後等待 DOM 更新，再讀最後一列。
// 輸入：newProduct。
// 副作用：更新列表並讀取 DOM。
products.value.push(newProduct)
await nextTick()
console.log(lastRow.value?.textContent)
```

- 交付前驗證：新增後最後一列內容正確；不加 nextTick 時能重現舊問題。
- 常見卡點：把 nextTick 當萬用解藥，掩蓋資料流設計錯誤。

### 主線專案銜接

今天理解新增商品後的 DOM 更新節奏。

1. 新增商品到列表。
2. 等待 DOM 更新。
3. 驗證最後一列。

檢查項目：state 已更新；DOM 更新時機正確；沒有過度依賴 DOM。

### 當天做完後檢查

- 多次 push 只造成一次畫面更新。
- nextTick 後讀到最新 DOM。
- console 順序符合預期。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| state | products | 新增資料 |
| 排程 | Vue update queue | 批次更新 |
| DOM | table row | 最終顯示 |

### 完整實作流程、範例與注意事項

1. 建立新增商品按鈕。
2. click 後 push 商品。
3. 在 push 前後 log DOM。
4. 加 `await nextTick()` 再 log。

注意事項：資料邏輯盡量用 state/computed 驅動，只有必要時才讀 DOM。

### 如果結果和預期不同

- nextTick 未定義：確認 import。
- DOM ref 為 null：確認元素已渲染。
- 還是讀舊值：確認讀的是正確元素。

### 負面例子 / 錯誤用法

錯誤做法：每次 state 修改後都無腦 `await nextTick()`。

問題：程式流程變慢且難懂。

修正方向：只有需要 DOM 結果時才用。

以為 JavaScript 每行跑完都會立刻重畫畫面。瀏覽器與 Vue 都會排程。

## Day 11：Vue 的 nextTick DOM 更新後回調

### 這篇文章主要在講什麼

這篇聚焦 `nextTick()` 的使用：狀態改完後，等待 Vue 完成 DOM patch，再做 focus、scroll、量測等操作。

### 為什麼需要這個概念

只要你的操作依賴「畫面真的更新後」的結果，就需要理解 nextTick。例如表單錯誤訊息顯示後 focus 到第一個錯誤欄位。

### 學完這篇你應該會做到什麼

```ts
// 範例用途：錯誤顯示後 focus 欄位。

errors.value = validateDraft(draft.value)
```

- 常見卡點：用 setTimeout 0，結果在不同瀏覽器或慢機器不穩。

### 主線專案銜接

今天完成表單錯誤 focus。

1. 驗證 draft。
2. 更新 errors。
3. nextTick 後 focus。

檢查項目：錯誤 DOM 存在；focus 目標正確；成功送出不執行。

### 當天做完後檢查

- 錯誤訊息顯示。
- focus 到第一個錯誤欄位。
- 沒有用 setTimeout 猜時機。

## Day 12：Vue 監聽器副作用的清除

### 這篇文章主要在講什麼

這篇說明 watcher 裡的副作用要能清除，特別是 API request、timer、event listener。否則舊請求可能蓋掉新結果。

### 為什麼需要這個概念

搜尋框快速輸入時，先送出的 request 可能比較晚回來。如果不取消或忽略舊 request，畫面會顯示過期結果。

### 學完這篇你應該會做到什麼

- 在 watch 中清理過期副作用。
- 用 `AbortController` 取消 fetch。
- 知道 Vue 3.5+ 可用 `onWatcherCleanup()`。

### 核心重點

- 每次 watcher 重新執行前，要處理上一輪副作用。
- fetch 可用 AbortController。
- timer / listener / subscription 都要清。

### 真實工作流程例子

- 工作任務：QA 回報快速輸入「iphone」後，結果偶爾顯示成「ip」。
- 你先判斷：這是 request race condition，不是搜尋演算法錯。
- 會動到：`useProductSearch.ts`、`productApi.ts`。
- 資料怎麼流：keyword 改變 -> 建立 controller -> request -> cleanup abort 舊 request -> 最新結果更新。
- 流程路線圖：輸入 -> watch -> fetch A -> 輸入變更 -> cleanup A -> fetch B -> results。
- 工作中會寫 / 檢查的片段：

```ts
// 範例用途：取消過期搜尋請求。
// 輸入：keyword。
// 副作用：只保留最新 request 結果。
watch(keyword, async (value, _old, onCleanup) => {
  const controller = new AbortController()
  onCleanup(() => controller.abort())
  results.value = await productApi.search(value, { signal: controller.signal })
})
```

- 交付前驗證：快速輸入只顯示最後關鍵字結果；Network 面板看到舊 request 被取消。
- 常見卡點：catch 到 abort error 後仍顯示錯誤 toast。

### 主線專案銜接

今天讓搜尋 request 可取消。

1. 在 service 支援 signal。
2. 在 watcher 建立 controller。
3. cleanup 時 abort。

檢查項目：舊 request 不覆蓋新資料；abort 不顯示一般錯誤；loading 最終正確。

### 當天做完後檢查

- 快速輸入不亂序。
- abort request 不被當成失敗提示。
- 最新搜尋結果正確。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| watcher | `useProductSearch.ts` | 建立與清除 request |
| API | `productApi.ts` | 接收 signal |
| UI | `ProductListView.vue` | 顯示最新結果 |

### 完整實作流程、範例與注意事項

1. 修改 `productApi.search(keyword, options)`。
2. 將 `signal` 傳給 fetch。
3. watcher 中建立 AbortController。
4. onCleanup abort。
5. catch abort 時忽略。

注意事項：取消 request 不等於所有後端都停止處理，但前端可避免使用過期結果。

### 如果結果和預期不同

- abort 報錯：檢查是否把 AbortError 當一般錯誤。
- 舊結果仍出現：確認每次 watch 都建立新的 controller。
- loading 卡住：finally 中要判斷最新 request。

### 負面例子 / 錯誤用法

錯誤做法：每次搜尋都發 request，但不取消也不檢查順序。

問題：晚回來的舊 request 會蓋掉新結果。

修正方向：使用 cleanup、AbortController 或 request id。

### 小練習

新增 debounce，並確認 debounce 與 abort 同時存在時結果仍正確。

### Junior 常見誤解

以為 await 就能保證最後輸入最後回來。網路回應順序不受 await 保證。

### 一句話總結

watcher 內的副作用要能清掉，否則舊任務會污染新狀態。

## Day 13：Vue 元件 emits 和 props 傳遞

### 這篇文章主要在講什麼

這篇說明 Vue 元件溝通：父層透過 props 給子層資料，子層透過 emits 通知父層事件。這是單向資料流的基礎。

### 為什麼需要這個概念

如果子元件直接改父層資料，元件邊界會變模糊。真實專案會變成「不知道是誰改了資料」，排錯很痛苦。

- 定義 props 與 emits 型別。
- 子元件不直接改 props。
- 父層負責資料更新決策。

### 核心重點

- props 是輸入。
- emits 是事件。
- 子層回報意圖，不直接決定父層狀態。
- 在 VS Code 實作時，通常會把父層頁面放在 `src/views/ProductEditorView.vue`，把子層表單放在 `src/components/ProductForm.vue`；不要為了方便把父子邏輯都塞在同一個 `.vue` 檔。

### 真實工作流程例子

- 工作任務：商品表單子元件要送出資料給編輯頁，由編輯頁決定呼叫新增或更新 API。
- 你先判斷：表單只負責收集資料，不負責知道 API endpoint。
- 會動到：`ProductForm.vue`、`ProductEditorView.vue`。
- 資料怎麼流：editor 傳 initialValue -> form 建 draft -> form emit submit -> editor 呼叫 store save。
- 流程路線圖：父層資料 -> props -> 子層表單 -> emit -> 父層 save -> store。
- 工作中會寫 / 檢查的片段：

```ts
// ProductForm.vue
// 範例用途：定義表單送出事件。
// 輸入：draft。
// 副作用：通知父層，自己不打 API。
const emit = defineEmits<{ submit: [draft: ProductDraft] }>()
function onSubmit() {
  emit('submit', draft.value)
}
```

- 交付前驗證：表單 submit 時父層收到 draft；子層沒有 import store。
- 常見卡點：子層同時 emit 又自己改 store，造成重複更新。

- 父層能處理 submit。
- 子層不直接改 props。
- payload 包含必要欄位。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 子元件 | `ProductForm.vue` | 收集資料與 emit |
| 父頁面 | `ProductEditorView.vue` | 決定儲存流程 |
| Store | `productStore.ts` | 實際更新資料 |

### 完整實作流程、範例與注意事項

1. 定義 `ProductDraft`。
2. ProductForm 接 `initialValue`。
3. 建立 local draft。

5. 父層接事件呼叫 store。

問題：子層直接改父層資料，資料流失控。

## Day 14：Vue 元件 Props 與 customRef

### 這篇文章主要在講什麼

這篇談 props 驗證與 `customRef()`。props 是元件外部契約；customRef 則讓你自訂 ref 的追蹤與觸發時機，例如 debounce。

### 為什麼需要這個概念

工作中搜尋欄很常需要 debounce。若每打一個字都觸發搜尋，API 壓力大、畫面也容易閃爍。

### 學完這篇你應該會做到什麼

- 定義清楚 props 型別。
- 用 customRef 封裝 debounce input。
- 知道 customRef 不該藏複雜業務。

### 核心重點

- props 是元件 API。
- customRef 可控制 track/trigger。
- debounce 是 customRef 常見例子。
- 在 VS Code 裡，`customRef` 這類可重用邏輯通常放進 `src/composables/useDebouncedRef.ts`，不要直接藏在單一頁面元件裡，否則下一個搜尋框又要重寫一次。

### 真實工作流程例子

- 工作任務：搜尋框每輸入一字就打 API，後端要求前端 debounce 300ms。
- 你先判斷：這是輸入值更新節奏問題，可封裝成 `useDebouncedRef`。
- 會動到：`useDebouncedRef.ts`、`ProductListView.vue`。
- 資料怎麼流：input -> debounced ref -> watch -> API。
- 流程路線圖：輸入 -> customRef setter -> timer -> trigger -> watch -> search。
- 工作中會寫 / 檢查的片段：

```ts
// useDebouncedRef.ts
// 範例用途：延遲觸發 ref 更新，避免每個字都搜尋。
// 輸入：初始值與延遲毫秒。
// 回傳：可用於 v-model 的 debounced ref。
export function useDebouncedRef(value = '', delay = 300) {
  let timer: number | undefined
  return customRef<string>((track, trigger) => ({
    get() { track(); return value },
    set(newValue) {
      clearTimeout(timer)
      timer = window.setTimeout(() => { value = newValue; trigger() }, delay)
    },
  }))
}
```

- 交付前驗證：快速輸入只在停止後搜尋；清空輸入也會更新。
- 常見卡點：timer 沒清掉，造成多次 trigger。

### 主線專案銜接

今天把搜尋欄改成 debounced ref。

1. 建立 `useDebouncedRef`。
2. keyword 改用 debounced ref。
3. watch keyword 搜尋。
4. 在 VS Code 中用 `Ctrl+P` 快速切換 `ProductListView.vue` 與 `useDebouncedRef.ts`，確認畫面和邏輯分開。

檢查項目：debounce 有效；timer 清理；watch 次數下降。

### 當天做完後檢查

- Network request 數量下降。
- 使用者停止輸入後才搜尋。
- props 型別清楚。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| composable | `useDebouncedRef.ts` | 控制更新節奏 |
| 搜尋頁 | `ProductListView.vue` | 使用 debounced keyword |
| watcher | `useProductSearch.ts` | 觸發 API |

### 完整實作流程、範例與注意事項

1. 新增 `useDebouncedRef`。
2. 將搜尋 input v-model 綁到 debounced ref。
3. watch debounced ref。
4. 開 Network 面板測試 request 次數。
5. 測試快速輸入與刪除。

注意事項：debounce 延遲太長會讓使用者覺得慢；通常 200-500ms 視場景調整。

### 如果結果和預期不同

- 仍每字搜尋：確認 watch 的是 debounced ref。
- 值不更新：檢查 customRef 的 trigger。
- 型別錯誤：確認 `window.setTimeout` 型別。

### 負面例子 / 錯誤用法

錯誤做法：在每個頁面手寫一份 debounce timer。

問題：重複、容易漏清、行為不一致。

修正方向：抽成 composable。

### 小練習

把 delay 改成可由 props 傳入，測試 100ms 與 500ms 差異。

### Junior 常見誤解

以為 debounce 是讓 API 變快。它不是變快，而是減少不必要請求。

### 一句話總結

customRef 適合封裝像 debounce 這種「何時觸發更新」的規則。

1. 檢查 Product 型別含 id。

3. 新增本地草稿時產生 temp id。
4. 測試刪除第一筆。
5. 測試排序與輸入框。

注意事項：index key 只適合完全靜態、永不排序刪除的列表。

### 如果結果和預期不同

- key 重複：檢查 API id 是否唯一。
- 新增項沒有 id：建立 client temp id。
- 仍錯位：檢查子元件是否直接共用同一份 draft。

### 負面例子 / 錯誤用法

錯誤做法：`:key="index"` 用在可刪除列表。

問題：刪除後 index 全部改變，Vue 會重用錯節點。

修正方向：使用穩定 id。

### 小練習

做一個可排序列表，分別用 index key 和 id key 觀察差異。

### Junior 常見誤解

以為 key 只是消除 warning。key 是 Vue 判斷元素身份的重要資訊。

## Day 18：JavaScript 工廠函式和 class

### 為什麼需要這個概念

- 用 factory 建立表單預設資料。
- 判斷何時不需要 class。
- 避免把 reactivity 藏在 class 深處。

### 核心重點

- factory 是回傳物件的函式。
- class 適合有明確行為與不變式的模型。
- Vue composable 很常像 factory。

### 真實工作流程例子

- 工作任務：新增商品頁、複製商品頁、測試都需要建立 ProductDraft。

```ts
// productFactory.ts
// 範例用途：集中建立商品表單預設值。

// 回傳：完整 ProductDraft。
export function createProductDraft(seed: Partial<ProductDraft> = {}): ProductDraft {

```

- 常見卡點：每頁各自寫預設值，欄位新增時漏改。

### 主線專案銜接

今天建立 draft factory。

1. 新增 `productFactory.ts`。

3. 測試使用 factory。

檢查項目：預設值一致；欄位集中；測試資料容易建立。

### 當天做完後檢查

- 新增頁能取得預設 draft。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 工廠 | `productFactory.ts` | 建立 draft |

| 測試 | `*.spec.ts` | 建立測試資料 |

### 完整實作流程、範例與注意事項

3. 新增頁呼叫 factory。
4. 複製頁傳 seed。
5. 測試預設值。

### 如果結果和預期不同

- 欄位 undefined：檢查 factory 是否補齊欄位。

- reactive 異常：確認是否需要在使用端再包 ref/reactive。

### 小練習

### Junior 常見誤解

## Day 19：Vue 組合式邏輯概念 Composable

### 這篇文章主要在講什麼

這篇介紹 composable：把可重用的狀態邏輯抽成 `useXxx()` 函式，例如搜尋、分頁、拖曳、API 請求。

### 為什麼需要這個概念

當元件同時處理畫面、API、搜尋、分頁、錯誤時會變很長。composable 能把邏輯拆出來，讓元件專心描述畫面。

### 學完這篇你應該會做到什麼

- 建立 `useProductSearch()`。
- 回傳 state 與操作函式。
- 在卸載時清理副作用。

### 核心重點

- composable 命名通常 `useXxx`。
- 可以回傳 ref、computed、function。
- 不要做成萬用 `useCommon`。

### 真實工作流程例子

- 工作任務：商品列表和庫存列表都需要搜尋、loading、error。
- 你先判斷：這是可重用行為，抽 composable，而不是複製貼上。
- 會動到：`useProductSearch.ts`、兩個 view。
- 資料怎麼流：view 呼叫 composable -> composable 管 state -> view 顯示。
- 流程路線圖：需求 -> composable -> keyword/loading/error/results -> view template。
- 工作中會寫 / 檢查的片段：

```ts
// useProductSearch.ts
// 範例用途：封裝商品搜尋狀態與操作。
// 輸入：searcher 函式。
// 回傳：view 可使用的狀態與 search 方法。
export function useProductSearch(searcher: (q: string) => Promise<Product[]>) {
  const keyword = ref('')
  const results = ref<Product[]>([])
  const loading = ref(false)
  async function search() {
    loading.value = true
    results.value = await searcher(keyword.value)
    loading.value = false
  }
  return { keyword, results, loading, search }
}
```

- 交付前驗證：兩個頁面都能用；修改搜尋邏輯只改 composable。
- 常見卡點：composable 偷偷 import 特定頁面元件，變得不可重用。

### 主線專案銜接

今天把搜尋邏輯抽出。

1. 建立 `useProductSearch`。
2. ProductList 使用它。
3. InventoryList 也能使用。

檢查項目：沒有重複 loading/error；回傳 API 清楚；可測試。

### 當天做完後檢查

- 元件變短。
- 搜尋行為集中。
- composable 沒有 UI 相依。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| composable | `useProductSearch.ts` | 搜尋邏輯 |
| service | `productApi.ts` | 實際 API |
| view | `ProductListView.vue` | 顯示 UI |

### 完整實作流程、範例與注意事項

1. 找出元件中搜尋相關 state。
2. 搬到 composable。
3. 回傳 view 需要的資料。
4. view import composable。
5. 測試搜尋。

注意事項：composable 不應知道 UI 樣式或 route 細節，除非它就是 router composable。

### 如果結果和預期不同

- 多頁 state 互相影響：確認 composable state 是否在函式內建立。
- 測試困難：把 API 函式用參數注入。
- 型別太鬆：補上回傳型別。

### 負面例子 / 錯誤用法

錯誤做法：把所有專案邏輯塞進 `useProduct()`。

問題：composable 變成大型隱形元件。

修正方向：依責任拆成 search、pagination、selection。

### 小練習

抽出 `usePagination()`，回傳 page、pageSize、next、prev。

### Junior 常見誤解

以為 composable 一定要共用才值得寫。即使只給單頁用，也能讓元件更清楚。

### 一句話總結

composable 是把可重用或可分離的狀態邏輯抽出元件。

## Day 20：provide/inject 和 Pinia

### 這篇文章主要在講什麼

這篇介紹跨層資料傳遞：`provide/inject` 適合局部元件樹依賴；Pinia 適合跨頁、跨功能的全域狀態管理。

### 為什麼需要這個概念

如果所有資料都用 props 一層層傳，會變成 props drilling；如果所有資料都丟 Pinia，又會讓局部狀態全域化。要知道兩者邊界。

### 學完這篇你應該會做到什麼

- 用 provide/inject 傳遞局部 context。
- 用 Pinia 管理商品資料。
- 分辨局部依賴與全域狀態。

### 核心重點

- provide/inject 適合 form、table、theme context。
- Pinia 適合 auth、cart、product cache。
- 解構 Pinia state 時用 `storeToRefs()`。

### 真實工作流程例子

- 工作任務：商品表單底下有多層欄位元件，都需要知道是否 readonly。
- 你先判斷：readonly 是表單局部 context，用 provide/inject；商品列表資料跨頁共享，用 Pinia。
- 會動到：`ProductForm.vue`、`FormField.vue`、`productStore.ts`。
- 資料怎麼流：form provide readonly -> field inject readonly；store 提供 products 給頁面。
- 流程路線圖：表單設定 -> provide -> 子欄位 inject -> UI disabled；API -> Pinia -> pages。
- 工作中會寫 / 檢查的片段：

```ts
// ProductForm.vue
// 範例用途：提供表單局部 readonly 狀態。
// 輸入：readonly prop。
// 副作用：子欄位可 inject 並決定 disabled。
const formReadonlyKey = Symbol('formReadonly')
provide(formReadonlyKey, computed(() => props.readonly))
```

- 交付前驗證：readonly 時所有欄位 disabled；跨頁商品資料由 Pinia 保持。
- 常見卡點：把只屬於表單的 readonly 放進全域 store。

### 主線專案銜接

今天建立 Pinia store 與表單 context。

1. 安裝 Pinia。
2. 建立 `productStore`。
3. 表單用 provide/inject 傳 readonly。

檢查項目：store state 可見；局部 context 不污染全域；子欄位能注入。

### 當天做完後檢查

- products 可跨頁使用。
- readonly 能跨層傳遞。
- storeToRefs 使用正確。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| Store | `productStore.ts` | 跨頁商品狀態 |
| Provider | `ProductForm.vue` | 局部 readonly |
| Injector | `FormField.vue` | 使用 readonly |

### 完整實作流程、範例與注意事項

1. `npm install pinia`。
2. `main.ts` 註冊 pinia。
3. 建立 product store。
4. Form provide readonly。
5. Field inject readonly。

注意事項：不要把每個小狀態都放 Pinia；全域狀態越多，追蹤成本越高。

### 如果結果和預期不同

- store undefined：確認 `app.use(createPinia())`。
- inject undefined：確認 key 相同且有 provider。
- 解構失去響應：用 `storeToRefs()`。

### 負面例子 / 錯誤用法

錯誤做法：所有表單欄位狀態都放全域 Pinia。

問題：離開頁面後殘留，跨頁互相污染。

修正方向：局部狀態留元件或 provide/inject，全域共享才進 store。

### 小練習

把商品列表載入狀態放 Pinia，把表單 readonly 留 provide/inject。

### Junior 常見誤解

以為 Pinia 是 Vue 必備。小元件局部狀態不需要 store。

### 一句話總結

provide/inject 管局部跨層依賴，Pinia 管跨頁共享狀態。

## Day 22：SOLID OCP 和 Vue 元件開發

### 這篇文章主要在講什麼

這篇把 OCP 開放封閉原則放進 Vue：元件應該對擴充開放、對修改封閉。常見做法是 props、slot、schema、策略函式。

### 學完這篇你應該會做到什麼

- 找出元件變化點。

```ts
// productColumns.ts

export const productColumns = [
```

3. table 迭代 columns。

### Junior 常見誤解

## Day 23：SOLID LSP 和 Vue 組合式函式擴充

### 這篇文章主要在講什麼

這篇用 LSP 里式替換原則思考 composable：不同實作如果宣稱提供同一種能力，就應該能被替換而不破壞使用者。

### 為什麼需要這個概念

同一個 select 元件可能吃靜態選項，也可能吃 API 選項。如果兩種 composable 回傳格式不同，使用端就要寫很多分支。

### 學完這篇你應該會做到什麼

- 為 composable 定義共同回傳契約。
- 替換資料來源而不改 UI。
- 避免相似 API 有不同語意。

### 核心重點

- 替換實作不應破壞呼叫端。
- 回傳 shape 要一致。
- loading/error/refresh 語意要一致。

### 真實工作流程例子

- 工作任務：商品分類 select 原本是靜態陣列，現在改從 API 載入，但 UI 不想改。
- 你先判斷：維持 composable 回傳契約，替換內部實作。
- 會動到：`useStaticOptions.ts`、`useRemoteOptions.ts`、`CategorySelect.vue`。
- 資料怎麼流：select 呼叫 useOptions -> options/loading/error -> template。
- 流程路線圖：資料來源變更 -> composable 替換 -> 同一 UI contract -> select 正常。
- 工作中會寫 / 檢查的片段：

```ts
// 範例用途：固定選項 composable 的回傳契約。
// 輸入：無或 API。
// 回傳：UI 可穩定使用的 options/loading/error/refresh。
type UseOptionsResult = {
  options: Ref<Option[]>
  loading: Ref<boolean>
  error: Ref<string | null>
  refresh: () => Promise<void>
}
```

- 交付前驗證：靜態與 API 版本都能給同一個 select 用。
- 常見卡點：其中一版沒有 refresh，UI 被迫判斷。

### 主線專案銜接

今天固定分類選項契約。

1. 定義 `UseOptionsResult`。
2. 靜態選項符合契約。
3. API 選項也符合契約。

檢查項目：CategorySelect 不改；兩種實作可替換；錯誤狀態一致。

### 當天做完後檢查

- select 不知道資料來源。
- API/靜態可替換。
- 回傳欄位一致。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 契約 | `types/options.ts` | 定義回傳格式 |
| 靜態實作 | `useStaticOptions.ts` | 本地資料 |
| 遠端實作 | `useRemoteOptions.ts` | API 資料 |
| UI | `CategorySelect.vue` | 使用契約 |

### 完整實作流程、範例與注意事項

1. 定義共同型別。
2. 改靜態 composable 回傳完整欄位。
3. 新增遠端 composable。
4. CategorySelect 只依賴共同契約。
5. 切換實作測試。

注意事項：LSP 重點是使用端期待不被破壞，不是所有實作內部都一樣。

### 如果結果和預期不同

## Day 26：JavaScript 錯誤處理和 onErrorCaptured

### 這篇文章主要在講什麼

這篇介紹 JavaScript 錯誤處理與 Vue 的 `onErrorCaptured()`。它可以在父元件捕捉子元件錯誤，避免整個頁面直接崩掉。

### 為什麼需要這個概念

後台系統不能因為某張商品卡片渲染失敗就整頁白屏。錯誤邊界可以讓局部區塊顯示 fallback，同時記錄錯誤。

### 學完這篇你應該會做到什麼

- 區分可預期錯誤與程式錯誤。
- 建立 ErrorBoundary。
- 使用 `app.config.errorHandler` 做全域紀錄。

### 核心重點

- API 錯誤應轉成 UI 狀態。
- 程式錯誤可用 error boundary 捕捉。
- `onErrorCaptured` 回傳 false 可阻止向上傳播。

### 真實工作流程例子

- 工作任務：商品詳情子元件偶發錯誤，要求不要整頁白屏，並顯示局部錯誤訊息。
- 你先判斷：這是元件渲染錯誤邊界，不是一般表單驗證錯誤。
- 會動到：`ErrorBoundary.vue`、`ProductDetailView.vue`、`main.ts`。
- 資料怎麼流：子元件 throw -> boundary captured -> error state -> fallback UI -> logger。
- 流程路線圖：子元件錯誤 -> onErrorCaptured -> fallback -> log -> 使用者可返回。
- 工作中會寫 / 檢查的片段：

```ts
// ErrorBoundary.vue
// 範例用途：捕捉子元件錯誤並顯示 fallback。
// 輸入：slot 子元件。
// 副作用：記錄錯誤並顯示錯誤狀態。
const error = ref<Error | null>(null)
onErrorCaptured(err => {
  error.value = err as Error
  return false
})
```

- 交付前驗證：子元件 throw 時顯示 fallback；console 或 logger 有紀錄。
- 常見卡點：把 API 404 也當成程式錯誤丟出，使用者體驗差。

### 主線專案銜接

今天建立商品詳情錯誤邊界。

1. 建立 `ErrorBoundary`。
2. 包住 `ProductDetailPanel`。
3. 設定全域 errorHandler。

檢查項目：局部錯誤不白屏；錯誤可重現；log 有上下文。

### 當天做完後檢查

- fallback 顯示。
- 其他區塊仍可操作。
- 錯誤有紀錄。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| ErrorBoundary | `components/ErrorBoundary.vue` | 捕捉子錯誤 |
| 詳情頁 | `ProductDetailView.vue` | 使用 boundary |
| 全域 | `main.ts` | 記錄未捕捉錯誤 |

### 完整實作流程、範例與注意事項

1. 建立 ErrorBoundary。
2. 用 slot 包子元件。
3. error 不為 null 時顯示 fallback。
4. 在 main 設定 errorHandler。
5. 寫測試元件丟錯驗證。

注意事項：錯誤邊界不是讓錯誤消失；要顯示、記錄、排查。

### 如果結果和預期不同

- 整頁仍白屏：確認 boundary 是否包到出錯元件。
- 沒有 log：檢查 errorHandler 或 logger。
- API 錯誤顯示不對：區分 API state 與 render error。

### 負面例子 / 錯誤用法

錯誤做法：所有 catch 都空白吞掉。

問題：使用者看不到結果，工程師也查不到問題。

修正方向：顯示 fallback，並記錄錯誤上下文。

### 小練習

### Junior 常見誤解

以為 try/catch 可以抓所有 Vue render error。元件樹錯誤要理解 Vue 的捕捉機制。

### 一句話總結

2. 加分頁或 virtual list。
3. 穩定 props。

檢查項目：效能數據改善；功能不退化；優化理由有紀錄。

### 當天做完後檢查

- 大量資料可操作。
- 搜尋不明顯卡頓。
- 沒有不必要 inline object。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 資料推導 | computed | 篩選與分頁 |
| 表格 | `ProductTable.vue` | 渲染可見資料 |
| 工具 | Devtools / Performance | 量測 |

### 完整實作流程、範例與注意事項

1. 準備 3000 筆測試資料。
2. 用 Performance 錄製搜尋。
3. 改成分頁或 virtual list。
4. 移除不穩定 props。
5. 再量測比較。

注意事項：效能優化要留下原因，不要把程式變難懂卻沒有收益。

### 如果結果和預期不同

- 還是慢：檢查是否 filter 本身太重。
- row 一直更新：檢查 props 是否每次新建。
- DOM 太多：改分頁或虛擬列表。

### 負面例子 / 錯誤用法

錯誤做法：看到卡就到處加 `v-memo`。

問題：可能掩蓋真正瓶頸，還讓狀態更新變難理解。

修正方向：先量測，再選策略。

### 小練習

比較 3000 筆直接渲染、每頁 50 筆、virtual list 的差異。

### Junior 常見誤解

以為 re-render 都是錯。正確 re-render 是框架正常工作；不必要或過大的 render 才是問題。

### 一句話總結

Vue 效能優化要先量測，再針對資料量、依賴與 DOM 數量下手。

## Day 29：Vue CSR、SSR 和通用渲染模式

### 這篇文章主要在講什麼

這篇比較 CSR、SSR 與通用渲染。CSR 在瀏覽器產生畫面；SSR 先在伺服器產生 HTML；通用渲染代表同一份 Vue 程式會在 server/client 兩邊跑。

### 為什麼需要這個概念

不是每個 Vue 專案都需要 SSR。內部後台通常 CSR 足夠；公開商品頁若重視 SEO、首屏速度與社群預覽，可能需要 SSR 或 SSG。

### 學完這篇你應該會做到什麼

- 判斷 CSR/SSR/SSG 適用情境。
- 知道 SSR 不能隨便用 `window`。
- 知道 Nuxt 是常見 SSR/SSG 方案。

### 核心重點

- CSR：部署簡單，SEO 需額外處理。
- SSR：首屏與 SEO 較好，但架構複雜。
- SSG：適合內容相對固定的公開頁。

### 真實工作流程例子

- 工作任務：商品詳情頁要讓搜尋引擎收錄，後台管理頁不用。
- 你先判斷：後台維持 CSR；公開商品頁評估 SSR/SSG。
- 會動到：架構文件、router、可能的 Nuxt 專案或 SSG 流程。
- 資料怎麼流：request -> server render 或 static HTML -> hydration -> client interaction。
- 流程路線圖：SEO 需求 -> 頁面分類 -> CSR/SSR/SSG 決策 -> 部署策略。
- 工作中會寫 / 檢查的片段：

```text
決策檢查：
- 需要登入後才看：CSR
- 公開且需要 SEO：SSR 或 SSG
- 內容更新頻率低：SSG
- 高互動後台：CSR
```

- 交付前驗證：公開頁 HTML source 有主要內容；後台 CSR build 正常。
- 常見卡點：SSR 中直接使用 `window.localStorage`，server 端爆錯。

### 主線專案銜接

今天做渲染模式決策。

1. 將頁面分成公開頁與後台頁。
2. 後台維持 CSR。
3. 公開商品詳情列入 SSR/SSG 評估。

檢查項目：需求有 SEO 才升級；SSR 限制有列出；部署成本有估。

### 當天做完後檢查

- 能說明為什麼後台不需要 SSR。
- 能列出公開頁 SSR/SSG 優缺點。
- 能找出瀏覽器 API 使用風險。

### 範例範圍地圖

| 部分 | 位置 | 責任 |
| --- | --- | --- |
| 後台 SPA | Vite Vue | CSR |
| 公開頁 | Nuxt/SSG | SEO 與首屏 |
| 文件 | `docs/rendering-decision.md` | 記錄決策 |

### 完整實作流程、範例與注意事項

1. 列出所有頁面。
2. 標記是否公開、是否需 SEO。
3. 標記資料更新頻率。
4. 選 CSR/SSR/SSG。
5. 記錄決策與限制。

注意事項：SSR 不是免費加速，它會帶來 server 成本、快取、hydration 與跨 request 狀態問題。

### 如果結果和預期不同

- SSR 爆 window undefined：把瀏覽器 API 放 client-only。
- hydration mismatch：檢查 server/client 初始資料是否一致。
- SEO 還不好：確認 HTML source 是否有內容。

### 負面例子 / 錯誤用法

錯誤做法：因為聽起來高級，把內部後台全改 SSR。

問題：成本上升，但 SEO 幾乎沒有價值。

修正方向：根據頁面需求選渲染模式。

### 小練習

為商品工作台列出 5 個頁面，逐一選 CSR、SSR 或 SSG 並寫理由。

### Junior 常見誤解

以為 SSR 一定比 CSR 快。SSR 只改善某些場景，互動後仍要 hydration。

### 一句話總結

渲染模式要依 SEO、首屏、互動與部署成本選擇。
