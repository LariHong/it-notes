# 筆記知識點補充

## 目標

把使用者讀筆記時不懂的知識點，整理成獨立的補充 Markdown，並讓原筆記維持主線閱讀節奏。

最重要規則：補充連結一定要放在原筆記「對應的 Day / 段落」內，不能集中放到原檔最下面。

## 需要的資訊

優先從使用者訊息與本機檔案推斷，能安全推斷時不要反覆詢問：

- 原筆記檔案，例如 `Vue3_30天自我學習指南_2026更新整理.md`
- 對應 Day 或段落，例如 `Day 1`
- 一個或多個知識點，例如 `createApp()`、`mount()`

如果找不到使用者指定的 Day / 段落，先搜尋合理變體，例如 `## Day 1`、`## Day 01`、`## Day 1：...`。仍找不到時，再請使用者提供精確標題。

## 工作流程

1. 檢查原筆記。
   - 找到目標 Day / 段落標題。
   - 找到下一個同層或更高層標題，確認該 Day / 段落的範圍。
   - 編輯範圍要限制在該 Day / 段落內。

2. 先決定資料夾結構。
   - 預設必須建立資料夾，資料夾名稱用原筆記檔名去掉 `.md`。
   - 原筆記與知識點補充筆記必須放在同一資料夾內。
   - 如果原筆記已經在資料夾內，優先沿用既有資料夾。
   - 若使用者明確要求不要移動檔案，才可不整理成資料夾。
   - 在開始寫補充檔前，先確認最終路徑，避免先在根目錄建立再忘記移動。

3. 決定補充筆記名稱。
   - 如果使用者指定補充筆記檔名，優先使用指定名稱。
   - 如果沒有指定，從主題推導，並在檔名後加上 `知識點補充.md`。
   - Vue 範例中，使用者指定時可使用 `Vue3_手把手教學_2026更新整理知識點補充.md`。

4. 建立或更新補充筆記。
   - 保留既有內容，不要覆蓋整份檔案。
   - 如果對應 Day 已存在，就在該 Day 底下新增或更新知識點。
   - 如果同一知識點已存在，就更新既有段落，不要重複新增。
   - 更新既有段落時，先審視目前內容缺口，再局部擴寫或修正；不要不看內文就直接用一段全新版本替換。
   - 使用穩定的 Markdown 標題，方便原筆記用錨點連結。
   - 補充筆記可以包含使用者所有要求補充的知識點；但原筆記回填連結不一定要全部列出，必須依使用者指定的回填範圍處理。

5. 回到原筆記的對應 Day / 段落加連結。
   - 在該 Day / 段落內新增或更新 `### 知識點補充`。
   - 裡面只放簡潔的知識點連結清單。
   - 連結清單只放使用者明確要求「放回原筆記」的知識點；若使用者沒有區分補充範圍與回填範圍，才放全部本次補充知識點。
   - 建議位置：放在 `### 核心重點` 之後，或放在檢查、練習、小結之前。
   - 嚴禁把補充連結放到整份原筆記最下面。

6. 更新 `README.md`。
   - `README.md` 是 repository 的筆記索引。
   - 若原本直接連到主筆記，改成連到資料夾內的主筆記。
   - 除非 README 既有慣例會列出補充檔，否則 README 只列主筆記即可。

7. 使用 GitHub 發布。
   - 只有在使用者要求或語意明確包含「上傳 GitHub / 發布 / push」時才發布。
   - Markdown 整理完成後，銜接既有 `github-markdown-publisher` Skill。
   - 發布前檢查 git status，避免 stage 無關檔案。
   - 只 stage 這次移動、新增、修改的 Markdown 與 README。
   - 除非使用者明確要求發布 Skill 本身，否則不要把 `skills/**/SKILL.md` 這類內部 Skill 檔案一起發布。

## 補充筆記格式

補充筆記建議使用這個結構：

````markdown
# <主題> 知識點補充

## Day N：<Day 標題>

### <知識點>

#### 1. 知識點

用 junior developer 容易理解的方式說明核心概念。

#### 2. 使用注意

- 說明常見限制、順序、時機、錯誤訊息或踩坑。
- 說明它和原筆記 Day 內容的關係。

#### 3. 工作上常用知識

- 說明實務專案中會在哪裡看到。
- 說明 code review、debug、維護或架構判斷時怎麼用。

#### 4. 常見誤解

- 說明初學者常見錯誤理解。

#### 5. 小範例

```ts
// 範例要能讓沒學過的 junior 看懂怎麼操作。
// 短概念可以用短範例；流程、框架 API、父子元件、資料流、錯誤處理等主題要用較完整範例。
```
````

如果知識點不是程式碼概念，可以把小範例改成情境、流程或檢查清單。

## 範例撰寫規則

範例要依知識點難度調整，不要機械式只寫極短片段。

- 如果使用者明確說「看不懂」、「例子不完整」、「流程不清楚」、「給 junior 看」，範例必須補到可以跟著操作。
- 對 framework API、元件資料流、父子元件溝通、表單、狀態管理、API 呼叫、錯誤處理、重構流程等主題，優先使用完整情境範例，而不是只放 5 行 isolated snippet。
- 完整情境範例至少包含：檔案位置或檔名、輸入資料、狀態如何建立、使用者操作如何改變狀態、輸出或事件如何交給下一層、為什麼這樣設計。
- 程式碼註解要說明「操作意圖與原理」，例如 props 是父層輸入、emit 只是通知父層、local draft 避免直接修改 props、computed 依賴改變才重算。
- 範例可以分成多個檔案片段，例如 `types`、`composable`、子元件、父元件；每個片段都要標示檔名。
- 範例後要補一段「操作順序 / 資料流 / 原理」說明，讓 junior 能把程式碼和實際流程接起來。
- 若原本已有小範例但過短，先保留可用概念，再擴寫成完整例子；不要為了重寫而刪除正確內容。
- 避免只給抽象比喻。比喻可以輔助，但必須搭配可執行或可落地的程式碼、流程、檢查清單。

## 原筆記連結規則

從原筆記連到補充筆記時：

- 使用相對路徑。
- 使用補充筆記中的標題錨點。
- 連結文字要清楚可讀。

範例：

```markdown
### 知識點補充

- [createApp()](Vue3_手把手教學_2026更新整理知識點補充.md#createapp)
- [mount()](Vue3_手把手教學_2026更新整理知識點補充.md#mount)
```

如果原筆記與補充筆記已經移到同一資料夾，連結保持同資料夾相對路徑即可。

## 品質檢查

- 預設使用繁體中文撰寫。
- 原筆記只放連結索引，不要塞入大段補充內容。
- 補充筆記要實用，至少包含：知識點、使用注意、工作上常用知識、常見誤解、小範例或情境。
- 若知識點牽涉實作流程，範例要有足夠上下文、註解與操作順序，不能只放過小片段讓 junior 自己猜。
- 檢查是否有重複標題、重複連結。
- 移動資料夾後，檢查相對連結是否仍正確。
- 完成前一定要確認：補充連結位於原筆記對應 Day / 段落內，而不是原檔最下面。

## 執行前確認清單

在第一次編輯檔案前，先用一句話確認內部執行計畫：

- 原筆記最終路徑。
- 補充筆記最終路徑。
- 本次要寫進補充筆記的知識點清單。
- 本次要回填到原筆記的連結清單。
- README 要連到主筆記還是也列補充筆記。

如果「補充筆記知識點清單」和「原筆記回填連結清單」數量不同，必須明確指出這是因為使用者只要求部分知識點回填；若無法確定，先問使用者。

## 完成前確認清單

提交或回覆前，逐項確認：

- 原筆記與補充筆記在同一資料夾，或已記錄使用者要求不移動。
- 原筆記 Day / 段落內含 `### 知識點補充`，且沒有被加到整份文件最下面。
- 原筆記回填連結數量與使用者要求回填的知識點一致。
- 補充筆記中的每個回填錨點都能在該檔找到對應標題。
- 補充筆記的範例符合知識點難度；對流程型主題已包含檔案位置、註解、操作順序與資料流說明。
- README 連結指向移動後的主筆記路徑。
- Git stage 只包含本次任務相關 Markdown 與 README；除非使用者明確要求，不能 stage 其他未追蹤檔或 Skill 檔。
