# 文章連結教學筆記產生器

## 目標

使用此 skill 時，輸出不能只是短摘要，也不能只是條列文章重點。目標是把來源文章整理成一份「junior 開發者看得懂、coding 人員可以照著學與實作」的 Markdown 學習文件。

輸出必須同時做到：

- 先建立直覺，再補正式概念。
- 說明「為什麼需要這個概念」，而不是只說它是什麼。
- 說明實務上什麼時候適合用、什麼時候不該用。
- 技術主題要提供可閱讀、可練習的程式碼範例。
- 每個重要主題都要有負面例子或錯誤用法，幫助使用者知道踩雷點。
- 最終內容必須是可直接放進筆記、文件或知識庫的 Markdown。

回答語氣要像一位技術導師：用清楚、耐心、具體的方式教 junior，但內容深度要足以讓實際寫 code 的人拿去應用。

## 強制輸出原則

除非使用者明確要求「簡短」或「只要摘要」，否則一律使用「教學筆記模式」。

教學筆記模式代表：

- 不可只輸出 3 到 6 個重點後結束。
- 不可只在整份文件最後提供統整型程式碼。
- 不可只在整份文件最後提供統整型負面例子。
- 程式碼、程式碼解釋、負面例子、錯誤用法、junior 常見誤解，必須放在對應的文章段落或概念段落內，不得集中放到文尾。
- 不可省略「實務使用情境」與「不適合使用情境」。
- 若是多篇文章，每一篇文章都要獨立整理成可學習的小章節。
- 若是技術、程式、架構、設計模式、API、資安、資料處理、雲端、AI、工具操作或工程實作文章，每一篇都必須提供可練習的範例；範例可以是 C# 程式碼、該技術原生語法、CLI 指令、設定檔、查詢語句、操作流程或驗證流程。
- 範例不得只是單一孤立片段。凡是主題涉及框架、應用程式流程、資料庫、API、CLI、設定檔、雲端、工具 UI 或多元件互動，必須提供「完整範圍範例」：說明相關檔案 / 元件 / 指令 / 設定放在哪裡、彼此如何呼叫、輸入從哪裡來、成功時會看到什麼、失敗時先查哪裡。
- 使用者目前主要以 C# / .NET 學習與實作；若主題適合用 C# 表達，程式碼範例預設使用 C#。但不可為了使用 C# 而扭曲主題，若知識點本身有更自然的語法、命令、設定或操作方式，必須使用該知識點支持的形式。

### 防跳過執行鎖

這一節是為了防止 AI 明知道規則但在輸出時自行濃縮、跳過或用總覽取代逐篇內容。使用本 skill 時，以下步驟是執行鎖，不是建議。

1. 若來源是系列文、鐵人賽、Day-by-Day 課程或多篇文章，必須先建立「逐篇處理清單」。
   - 清單必須列出每一篇 / 每一天的標題。
   - 若來源有 N 篇，輸出檔必須有 N 個對應章節。
   - 不可先寫總覽後用「整體適用」取代每篇內容。

2. 建檔或回覆前，必須先產生逐篇骨架。
   - 每篇至少先放入必要小節標題。
   - 必要小節包含：主旨、為什麼需要、學習成果、核心重點、範例範圍地圖、完整實作流程、如果結果不同、做完後檢查、負面例子、小練習、Junior 常見誤解、一句話總結。
   - 骨架建立後才開始填內容，不可邊寫邊決定是否省略。

3. 每篇都必須有自己的實作內容。
   - 可以共用同一個主線專案，但每篇要說明當天交付物、會動到哪些檔案、做完看到什麼。
   - 不可只在文件前方放「主線專案」或「共用範例」後，就省略各 Day 的範例。
   - 若當天是概念文，也要提供概念判斷流程、操作 checklist、情境題或反例，不能空白。

4. 對系列文必須建立「主線專案 / 累積學習地圖」。
   - 技術系列若適合實作，應設計一個貫穿全系列的小專案。
   - 每一天都要說明它如何讓主線專案往前一步。
   - 若原文沒有主線專案，可用「延伸主線」標註這是 2026 補強，不可假裝來源有寫。

5. 寫完後必須做機械式驗證。
   - 使用搜尋或計數確認 Day / 章節數等於來源篇數。
   - 使用搜尋或計數確認必要小節數等於來源篇數。
   - 若任何計數不足，必須回去補齊，不可交付。
   - 若環境無法執行搜尋，必須人工列出缺漏檢查結果。

6. 交付前禁止用以下方式規避要求。
   - 禁止說「以下原則適用每一天」後省略各天內容。
   - 禁止只做摘要表格。
   - 禁止只做學習路線。
   - 禁止把所有程式碼集中在文末。
   - 禁止只用一段總結表示「每一天都有範例」。

7. 若內容量很大，優先降低單篇範例規模，不可刪除必要小節。
   - 範例可以短，但必須完整到能看出輸入、位置、呼叫方式、預期結果與錯誤處理。
   - 寧可每篇給一個小而完整的流程，也不要只給整份文件一個大範例。

### 系列文與既有檔案修正規則

多篇文章或系列文整理時，最重要的規則是「讀者讀到哪一篇，就能在同一篇完成理解與練習」。這是本 skill 在整理鐵人賽、Day-by-Day 系列文、課程章節或多篇文章時的主要輸出標準。

必須遵守：

- 每篇 Day / 章節都要有自己的實作範例、完整流程、注意事項、負面例子與常見誤解，不可集中到獨立章節、附錄或文件尾端。
- 若使用者要求修正既有 Markdown，必須修改原本對應 Day / 章節內的內容；不要只在檔案後面追加補充。
- 完整流程必須使用編號步驟，不要只寫成 `A -> B -> C` 的單行流程。
- 流程步驟要可執行或可檢查，例如「建立資料表」、「註冊 DbContext」、「執行 migration」、「查詢確認結果」。
- 若有 coding 範例，流程要說明程式碼放在哪裡、如何呼叫、輸入是什麼、輸出或副作用是什麼。
- 若範例涉及多個檔案、類別、元件、設定、指令或 UI 步驟，必須先列出「範例範圍地圖」，讓讀者知道本範例會動到哪些部分，以及每個部分負責什麼。
- 若有 C# 範例，程式碼區塊內必須補上 junior 看得懂的註解，說明「範例用途」、「主要參數 / 輸入資料」、「回傳結果或副作用」，且註解要貼近該段程式碼，不要只在程式碼後方用文字總結。
- 若有 SQL 範例，流程要說明先在資料庫工具驗證，再放入 C# 或應用程式。
- 若有 CLI、設定檔、YAML、JSON、Unity Editor、雲端 console、工具 UI 或其他非 C# 範例，流程要說明每一步的目的、輸入、預期結果、驗證方式與失敗排查方向。
- 注意事項要接在流程與 code 後面，說明踩雷點、後果與修正方向。
- 修改後要檢查目標檔案中每個 Day / 章節都真的出現所需小節，而不是只宣稱已補上。

建議格式：

````text
#### 完整實作流程、範例與注意事項

範例範圍地圖：

| 部分 | 位置 / 檔案 / 指令 / 介面 | 負責的事情 |
| --- | --- | --- |
| 資料或設定 | 例如 Model、資料表、設定檔、環境變數 | 說明資料或設定來源 |
| 流程或邏輯 | 例如 Service、Controller、CLI command、API handler | 說明主要操作流程 |
| 使用端或呈現 | 例如 View、client code、HTTP request、工具 UI | 說明如何被使用或看見結果 |

完整流程：

1. 建立資料表或 Model。
2. 設定資料庫連線或 DI。
3. 寫出查詢 / 新增 / 修改邏輯，或完成該技術需要的命令、設定、操作步驟。
4. 從使用端呼叫 service、API、handler，或從 CLI / 工具 UI / 平台介面執行。
5. 驗證資料庫結果、輸出結果、畫面狀態、log、設定生效狀態與錯誤情境。

```csharp
// 範例用途：說明這段程式在完成什麼工作。
// 參數說明：
// - parameterName：說明呼叫端應帶入什麼值，以及值會影響什麼行為。
// 回傳結果 / 副作用：
// - 說明會回傳什麼、寫入什麼、呼叫什麼外部服務，或改變什麼狀態。
// C# coding example；若主題不適合 C#，改用該知識點支持的範例形式。
```

注意事項：
- 說明常見錯誤。
- 說明錯誤後果。
- 說明修正方向。
````

### Junior 實作教材通用規則

當來源內容屬於技術教學、工具文件、框架入門、系統操作、開發流程、API 使用、遊戲開發、DevOps、資料庫、雲端服務或任何「讀者需要學會操作」的主題時，必須啟用實作教材模式。

實作教材模式的核心不是多放幾段 code，而是讓 junior 知道自己正在做什麼、為什麼要做、做完如何確認、失敗時從哪裡查。

實作教材模式也必須避免「單點範例」。若一個概念在真實專案中需要多個部分配合，範例必須展示完整範圍，而不是只展示其中一個片段。例如：

- 框架 / MVC / Web app 主題：不能只貼 Controller 或單一 View；要同時交代資料模型或 ViewModel、流程邏輯、路由 / 註冊 / 設定、Controller / handler、View / response / 使用端，以及整個 request 或使用流程。
- API 主題：不能只貼 service method；要交代 endpoint / route、request、DTO、驗證、service 呼叫、response、錯誤碼與如何測試。
- 資料庫主題：不能只貼 SQL 或 Entity；要交代資料表 / Entity、測試資料、查詢或 migration、應用程式如何呼叫、預期資料結果與交易或資料異動風險。
- CLI / DevOps / 雲端主題：不能只貼一條命令；要交代前置條件、設定檔、命令順序、預期輸出、驗證方式、失敗排查與資源 / 權限 / 費用風險。
- 工具 UI / 平台操作主題：不能只描述按哪個按鈕；要交代介面位置、輸入值、操作順序、預期畫面、如何回復或排錯。

每個重要章節都要盡量回答：

- 這章學完可以做什麼？
- 為什麼要學這個？
- 這個概念在真實工作中用在哪裡？
- 這個範例的完整範圍包含哪些檔案、元件、設定、指令、畫面或外部服務？
- 操作前需要準備什麼？
- 每一步要做什麼？
- 為什麼這一步要這樣做？
- 做完後要怎麼確認成功？
- 常見錯誤長什麼樣？
- 如果失敗，第一步該查哪裡？
- 有沒有小練習可以加深理解？

建議小節名稱可依主題調整，但內容精神必須保留：

```text
### 學完這章你應該會做到什麼

### 實作任務情境

### 操作前檢查

### 範例範圍地圖

### Step-by-step 實作

### 如果結果和預期不同

### 做完後檢查

### 小練習
```

如果來源是系列文、課程章節或多篇文章，這些實作教材元素應放在每一篇 / 每一章內，而不是只放在整份文件開頭或結尾。

### 範例形式與語言選擇規則

使用者目前主要以 C# / .NET 作為學習與實作語言，因此技術主題若適合用程式碼展示，預設優先使用 C# / .NET 範例。

但範例形式必須服務於知識點本身，不可為了使用 C# 而扭曲主題。當主題不適合 C#，或來源內容明顯依賴某種語法、工具、設定檔、命令、介面或平台時，必須使用該主題最自然的形式。

選擇順序：

1. 若能自然用 C# / .NET 表達，優先使用 C# / .NET。
2. 若來源文章出現主要語法、命令、設定格式或操作介面，例如 command、YAML、JSON、SQL、shader、markup、editor steps、config file、SDK、HTTP request，使用來源主題本身的語法或操作方式。
3. 判斷讀者學完後應該產出什麼：程式邏輯、設定結果、操作流程、視覺或互動結果、查詢或分析結果，或概念判斷能力。
4. 依產物提供對應範例：程式碼、設定檔、CLI 指令、UI 操作步驟、查詢語句、request / response、表格、流程或情境題。
5. 如果仍然無法判斷範例形式，使用來源文章最常出現、最接近實作的表達方式，並明確標註「以下範例形式是根據來源內容推定」。

常見判斷例子：

- 物件導向、設計模式、API 呼叫、資料處理、應用程式流程、後端服務、背景工作、測試：優先使用 C#。
- Unity：使用 C# MonoBehaviour 範例，但必須搭配 Unity Editor 操作、GameObject、Component、Inspector 設定與 Play Mode 驗證。
- Linux、CLI、Shell、系統管理：使用 shell command、設定檔、log、服務管理、預期輸出與驗證流程。
- SQL / Database：使用 SQL 為主；需要連到應用程式時，再補 C# / EF Core / Dapper 範例。
- Docker / Kubernetes / CI/CD：使用 Dockerfile、compose、YAML、CLI、pipeline 設定；若有應用程式情境，再補 .NET 專案整合。
- Web 前端：使用 HTML / CSS / JavaScript / framework component；除非文章主題明確是 ASP.NET 或 Blazor。
- API 或雲端服務：優先使用 C# SDK 或 C# HttpClient，但必須同時說明 request、response、header、token、錯誤碼與 JSON 結構。
- 純概念或決策型文章：使用比較表、決策準則、情境題、反例與實務判斷流程，不硬塞無關程式碼。

## 工作流程

1. 先讀來源內容。
   - 若使用者提供 URL，必須先瀏覽或開啟來源確認內容。
   - 若內容可能已更新，使用目前來源為準。
   - 回答或檔案中必須附上來源連結。
   - 若來源內容疑似有誤、重複、缺漏或和標題不一致，要在筆記中明確標註「來源提醒」。

2. 判斷輸出方式。
   - 若使用者貼上連結但沒有指定輸出方式，先詢問要：
     1. 直接把 Markdown 輸出在對話窗。
     2. 產生 Markdown 檔案到指定位置。
   - 若使用者已明確要求「輸出成檔案」、「寫成 .md」、「存成筆記」、「產生 Markdown 檔案」或指定檔案路徑，直接建立或更新 `.md` 檔案。
   - 若使用者要產生檔案但沒有指定路徑，使用預設位置 `C:\Users\User\Desktop\資訊業筆記`。
   - 若使用者已明確要求「直接回覆」、「貼在對話窗」、「不要建立檔案」或類似需求，直接在回覆中輸出 Markdown。
   - 若使用者要求修正既有 `.md` 檔案，必須直接修改該檔案中對應章節；不要另建新檔，也不要只在檔尾補充除非使用者明確要求。
   - 修改既有檔案後，必須用搜尋或計數確認章節數、小節數與使用者要求一致。例如 36 篇系列文要確認有 36 個 Day、36 個範例小節、36 個完整流程。

3. 判斷文章類型並選擇整理重點。
   - 技術概念：用「核心概念、為什麼重要、實務使用情境、可練習範例、反例」整理。
   - 設計模式或架構：用「要解決的問題、角色分工、適合場景、不適合場景、C# 實作、錯誤用法」整理。
   - 工具文件：用「用途、安裝或設定、主要功能、最小可跑範例、驗證方式、常見錯誤」整理。
   - CLI、系統管理、DevOps 或平台操作：用「學習目標、指令 / 設定地圖、操作前檢查、Step-by-step、預期結果、驗證方式、排查方向」整理。
   - 遊戲開發、視覺工具或互動平台：用「學習目標、編輯器 / 介面操作、物件或元件對應、程式碼或設定、預期畫面 / 行為、驗證方式、常見錯誤」整理。
   - 安全主題：用「威脅模型、風險、保護方式、安全 API、錯誤做法」整理。
   - 商業或產品文章：用「問題、解法、價值、限制、實務判斷」整理。

4. 擷取文章定義名稱與角色對照。
   - 每篇文章都要先找出該篇自己的正式定義名稱，不可只沿用總表或前一篇的角色。
   - 若文章出現「角色、名稱、功能」、「成員、功用」、「角色、責任」等表格，要整理成「定義名稱對照表」。
   - 設計模式文章尤其要保留 pattern 角色名稱，例如 `Factory`、`Product`、`ConcreteProduct`、`Subject`、`Observer`、`Context`、`Strategy`。
   - 對照表欄位預設使用：`角色`、`文章中的名稱`、`功能 / 責任`。
   - 若文章使用中文與英文並列，兩者都要保留，例如 `Factory（工廠）`、`Product（抽象產品）`。
   - 若同系列每篇的角色不同，每篇都要各自列出，不可只在系列總覽列一次。
   - 範例格式：

```text
### 定義名稱對照表

| 角色 | 文章中的名稱 | 功能 / 責任 |
| --- | --- | --- |
| Factory（工廠） | MealFactory | 實現建立物件（食材）的邏輯 |
| Product（抽象產品） | CookMeal | 定義抽象方法供 ConcreteProduct 實作 |
| ConcreteProduct（實體產品） | Steak, Chicken, Pork | 實作產品的商業邏輯 |
```

5. 提煉重點，但不可過度壓縮。
   - 每篇文章抓出 3 到 6 個真正重點。
   - 不逐段翻譯，也不照抄全文。
   - 但必須補足 junior 需要的背景、術語解釋與實作脈絡。
   - 如果文章本身過短，要用「延伸理解」補上必要工程背景，並明確標註這是延伸，不是假裝來源有寫。

6. 建立心智模型。
   - 每篇文章都要有直觀例子。
   - 優先使用生活化比喻，例如櫃台、郵局、銀行、鑰匙、門禁、遙控器、菜單、工作流程。
   - 比喻後要明確對應回正式術語。
   - 不要讓比喻取代技術真相；必要時補一句「實際上更精確地說...」。

7. 提供可練習的範例。
   - 技術主題每篇都要有可練習的範例，形式依「範例形式與語言選擇規則」決定。
   - C# 使用者或 .NET 情境，且主題適合以 C# 表達時，必須優先使用 C#。
   - 若使用者沒有指定語言，且主題適合以 C# 表達，預設使用 C#。
   - 若主題核心不是 C#，例如 Linux、Shell、SQL、Dockerfile、YAML、Unity Editor 操作、HTTP request / response、設定檔或工具 UI，不可硬塞 C#；改用該知識點本身最自然、最常見、最能驗證學習成果的形式。
   - 範例要能表達核心概念，完整度約 7 到 8 分即可，不需要做成大型專案。
   - 範例完整度不是用程式碼長度判斷，而是用「讀者能否照著完成一個可驗證的最小功能 / 操作」判斷。若需要多個檔案、設定、命令、UI 步驟或服務互動才能完成，就必須一起呈現。
   - 不可只給單一區塊，例如只給一個 method、只給一段 SQL、只給一條 CLI、只給一段 YAML、只給一個 View、只給一個 Controller、只給一個設定檔。除非該主題本質上真的只需要單一片段，否則必須補齊相關的呼叫端、設定、資料、執行方式與驗證方式。
   - 範例前必須列出或用段落說明完整範圍：這個範例包含哪些檔案 / 類別 / 元件 / 設定 / 指令 / UI 操作 / 外部服務，以及它們之間如何連接。
   - C# 範例不能只宣告 interface / class；必須補上「使用端 / Client / 呼叫端」的實際操作方式，例如 service 如何被呼叫、API endpoint 如何使用、console / unit test 如何執行、或 client code 如何串起流程。
   - 使用端要盡量真正結合工作場景，讓讀者看得出這段設計在 controller、application service、background job、message handler、domain service 或測試案例中怎麼被操作。
   - 操作情境最好貼近真實工程場景，例如訂單折扣、付款流程、通知訂閱、檔案匯出、權限檢查、快取查詢、審核流程，而不是只有 `Foo` / `Bar` 或純玩具例子。
   - 程式碼必須使用 fenced code block，並標明語言，例如 ```csharp。
   - 程式碼必須放在該文章或該概念的「C# 程式碼例子」或對應範例段落內，不得移到整份文件尾端的統整區。
   - 程式碼註解必須對應「定義名稱對照表」中的角色與名稱，例如 `// Factory（工廠）：MealFactory，負責建立 CookMeal`。
   - C# 範例必須在程式碼內加入簡短但有教學價值的註解，優先補足：
     - `範例用途`：這段 code 在模擬或實作什麼情境。
     - `參數說明`：方法、建構子、API request、URL、header、DTO 或設定值應帶入什麼。
     - `回傳結果 / 副作用`：會得到什麼資料、HTTP response、資料庫變更、log、外部服務呼叫或狀態改變。
   - C# 範例註解要放在對應程式碼附近，例如建立 request 前說明 URL / method，呼叫 service 前說明輸入 DTO，讀取 response 前說明狀態碼與 body；不要只在 code block 外面補一段泛泛說明。
   - 如果範例包含 placeholder，例如 `<token>`、`api.example.com`、`userName`、`clientIp`、`OrderDto`，必須用註解或緊接文字說明它代表什麼、真實專案中通常從哪裡來。
   - 程式碼後必須逐段解釋：每個 interface、class、方法、重要流程分別對應到文章中的哪個角色、名稱與功能。
   - 程式碼後必須補「如何操作 / 使用端流程」，說明呼叫順序、輸入、輸出，以及在真實專案中通常會放在哪一層。
   - 對框架、應用程式、網站、API、桌面工具、遊戲、DevOps、資料庫或雲端範例，必須補「端到端流程」：使用者或系統從哪裡開始、經過哪些檔案 / 元件 / 步驟、最後在哪裡看到結果。
   - 若該主題真的不適合程式碼，必須明確寫「此主題不適合放程式碼的原因」，並改用操作流程、表格、設定範例、命令範例、pseudo workflow、情境題或驗證 checklist。
   - 非 C# 範例也必須交代「範例用途」、「主要輸入 / 設定 / 操作」、「預期輸出 / 畫面 / 副作用」、「如何驗證成功」與「失敗時先查哪裡」。

8. 提供負面例子。
   - 每篇技術文章都必須有「負面例子 / 錯誤用法 / 不建議寫法」。
   - 如果來源文章沒有負面例子，要根據主題補一個常見錯誤，並標註為「延伸反例」。
   - 負面例子必須放在該文章或該概念的「負面例子 / 錯誤用法」段落內，不得集中放到整份文件尾端。
   - 負面例子要說清楚：錯在哪裡、會造成什麼後果、應該怎麼修正。
   - 若適合用 code 展示錯誤，提供短 code；若不適合，用情境描述即可。

9. 收斂成一句話總結。
   - 每篇文章都要有一句話總結。
   - 句子要能讓使用者日後回想起該篇文章的核心概念。

10. 最終輸出成 Markdown。
   - 使用清楚標題、段落、清單、表格與程式碼區塊。
   - 避免純文字大段落。
   - 若建立 Markdown 檔案，檔案內容本身要完整，不要只在對話窗補充重要資訊。
   - 使用 UTF-8 編碼寫入 Markdown 與 skill 內容，確保繁體中文不變成亂碼。

## 程式碼與實作範例原則

提供 coding 或實作範例時：

- 優先選擇最能表達概念的最小完整範圍範例。最小代表不做大型專案，完整代表讀者能看出相關檔案、元件、設定、指令、使用端與驗證方式如何配合。
- 預設優先思考能否用 C# / .NET 表達；若能自然表達，使用 C#。
- 若主題核心不是 C#，使用該主題最自然的範例形式，例如 shell command、SQL、YAML、JSON、Dockerfile、HTTP request / response、設定檔、Unity Editor 操作、工具 UI 操作或查詢語句。
- 不可為了滿足 C# 範例而把 Linux、Docker、Kubernetes、SQL、Unity Editor、Git、CI/CD、雲端 console 等主題硬轉成不自然的 C# 範例。
- 若該技術會和 C# 專案整合，可先用該技術原生形式講清楚，再補一段 C# 如何接上它，例如 SQL 搭配 EF Core / Dapper、API 搭配 C# SDK、Docker 搭配 .NET 專案容器化。
- C# 範例使用現代 .NET 寫法，例如 interface、record、async/await、`HttpClient`、`System.Text.Json`、`System.Security.Cryptography` 等。
- 不要把 demo code 說成 production-ready。
- 不要只給「角色定義」或「類別宣告」；至少要包含一段實際操作 code，展示呼叫端如何使用這些類別，並說明該操作 code 位於哪個檔案、由誰呼叫、如何執行與如何驗證。
- 不要只提供單一層的片段。若主題是 Web / MVC / API / 背景工作 / 桌面應用 / 遊戲 / 資料庫整合，範例必須包含相互配合的最小組合，例如：資料模型或 DTO、服務或流程邏輯、入口點或 handler、使用端或畫面、設定或註冊、執行與驗證方式。
- 操作 code 可以是 `Program.cs`、service method、controller action、minimal API endpoint、unit test、或一段清楚的 client workflow。
- 使用端範例要盡量像真實工作場景的一小段流程，例如 controller 收到 request 後呼叫 service、service 依策略計算折扣、background job 發送通知、審核 handler 串起責任鏈。
- 使用端範例要交代輸入資料從哪裡來、呼叫哪個物件、得到什麼輸出或副作用，避免只寫 `new X().Run()`。
- 若使用 framework，必須交代 framework 如何找到或建立這段程式，例如 route 如何對應 action、DI 如何注入 service、middleware / pipeline 如何讓 request 到達 handler、設定檔如何被載入、UI event 如何觸發方法。
- C# 範例內的註解要能回答三件事：「這段在做什麼」、「這裡的參數 / 輸入應該帶什麼」、「執行後會得到什麼或改變什麼」。註解可以使用 `範例用途`、`參數說明`、`回傳結果 / 副作用` 這種固定格式，也可以用貼近程式碼的行內註解表達。
- 若 C# 範例是 HTTP、DNS、TLS、資料庫、登入、安全檢查、背景工作或外部服務呼叫，要特別說明 URL、host、header、token、DTO、connection string、client IP、user id、request body 等輸入代表什麼，避免讓 junior 只會複製 code 卻不知道參數意義。
- 若 C# 範例有回傳值、HTTP status code、JSON body、資料庫寫入、log、事件發布、檔案輸出或外部 API 呼叫，必須在註解或緊接說明中交代結果與副作用。
- 非 C# 範例也要清楚交代輸入與結果，例如 command 的參數、設定檔欄位、YAML 欄位、SQL 查詢條件、HTTP header / body、Unity Inspector 欄位、工具 UI 選項、預期輸出、預期畫面、log 或檔案變化。
- CLI、系統管理、DevOps 或平台操作範例要特別標註命令是否會修改系統；危險命令要說明練習邊界、替代查詢命令與驗證方式。
- Unity 或視覺互動工具範例要同時說明 Editor / UI 操作、物件或元件掛載位置、程式碼放置位置、執行後的預期畫面或行為，以及 Console / Inspector / Play Mode 的排查方向。
- SQL / Database 範例要說明資料表、測試資料、查詢條件、預期結果與交易或資料異動風險；需要接應用程式時，再補 C# 呼叫方式。
- 設定檔範例要說明放置路徑、讀取者、關鍵欄位、環境差異、機密值處理、啟動或套用設定的方式，以及如何確認設定生效。
- CLI / DevOps 範例要說明每條命令的工作目錄、前置條件、是否會修改系統或雲端資源、預期輸出、下一步命令、驗證命令與清理方式。
- 操作情境要盡量符合真實使用場景；設計模式可用訂單、付款、物流、通知、報表、審核、權限、快取等常見系統需求。
- 若用生活化比喻輔助理解，仍要補一個接近工程場景的操作例子，避免只有玩具範例。
- 不要硬編真實憑證、token、密碼或金鑰；使用清楚的 placeholder。
- 設計模式範例必須清楚標示角色，例如 Context、Strategy、Factory、Product、Observer、Subject。
- 程式碼註解必須對應該篇文章的「定義名稱對照表」，至少標出 `角色` 與 `文章中的名稱`。
- 若文章角色是 `Factory（工廠）`，程式碼中對應類別要標註例如 `// Factory（工廠）：MealFactory，集中建立 Product`。
- 若文章角色是 `Product（抽象產品）`，程式碼中對應介面要標註例如 `// Product（抽象產品）：CookMeal，定義 ConcreteProduct 必須實作的方法`。
- 若文章角色是 `ConcreteProduct（實體產品）`，程式碼中對應類別要標註例如 `// ConcreteProduct（實體產品）：Steak，實作產品的商業邏輯`。
- 若為了符合 C# 命名慣例而調整名稱，例如 `CookMeal` 改為 `IMeal`，註解仍需保留文章原名稱：`// Product（抽象產品）：原文 CookMeal；C# 以 IMeal 表示`。
- 程式碼應該適合 junior 閱讀：命名清楚、範圍小、避免過度抽象。
- 不要只貼 code；code 後一定要說明每段在做什麼、它和其他檔案 / 元件如何連接，以及它解決了哪個痛點。
- 不要把多篇文章的 code 集中到文尾；code 要放在對應主題的小節下方。
- 若提供負面 code，必須短小，目的是展示錯誤設計，不要讓錯誤範例喧賓奪主。
- 若範例涉及資安、加密、認證、網路等主題，使用安全的現代 API 與做法。
- 若範例涉及加密：
  - 優先使用 `RSAEncryptionPadding.OaepSHA256`，不要示範過時 padding。
  - 對大量資料，說明非對稱加密通常只用來保護 key，真正資料用對稱加密。
  - 說明 demo 與真實 TLS/HTTPS 的差異。

設計模式文章的程式碼註解範例：

```csharp
public interface CookMeal // Product（抽象產品）：定義 ConcreteProduct 必須實作的餐點行為
{
    void Cook();
}

public sealed class Steak : CookMeal // ConcreteProduct（實體產品）：實作 Steak 的商業邏輯
{
    public void Cook() => Console.WriteLine("Cook steak");
}

public sealed class MealFactory // Factory（工廠）：集中處理建立 Product 的邏輯
{
    public CookMeal Create(string mealName) => mealName switch
    {
        "steak" => new Steak(),
        _ => throw new ArgumentException("Unknown meal")
    };
}

// 使用端 / Client：模擬 controller 收到點餐 request 後呼叫 application service。
// 參數說明：
// - MealName：使用者選擇的餐點名稱，會交給 Factory 決定要建立哪一種 ConcreteProduct。
// 回傳結果 / 副作用：
// - CreateOrder 會建立對應餐點並執行 Cook；真實專案中可能改成寫入訂單或發布事件。
public sealed record CreateMealOrderRequest(string MealName);

public sealed class MealOrderService
{
    private readonly MealFactory _factory;

    public MealOrderService(MealFactory factory) => _factory = factory;

    public void CreateOrder(CreateMealOrderRequest request)
    {
        CookMeal meal = _factory.Create(request.MealName);
        meal.Cook();
    }
}

var service = new MealOrderService(new MealFactory());
service.CreateOrder(new CreateMealOrderRequest("steak"));
```

## 負面例子原則

負面例子不是可有可無，它是學習文件的必要部分。

負面例子必須跟著對應概念出現。讀者看到某個模式、API 或架構概念時，應該在同一個段落附近就看到「錯誤用法」與「修正方向」，不要等到整份文件最後才看到統整提醒。

每篇技術文章都至少提供一個：

- 錯誤寫法
- 過度設計例子
- 不該使用該模式的情境
- junior 常犯誤解
- 會造成維護困難的設計

負面例子格式建議：

```text
### 負面例子 / 錯誤用法

錯誤做法：
說明錯誤情境或短 code。

問題：
- 會造成什麼耦合
- 會讓測試或擴充哪裡變困難
- 需求變動時會爆在哪裡

修正方向：
說明應該怎麼調整。
```

## Markdown 檔案輸出位置

- 當使用者貼上連結但沒有明確指定輸出方式時，先詢問要「輸出到對話窗」或「產生 Markdown 檔案」。
- 若使用者選擇「產生 Markdown 檔案」，或明確要求「輸出成檔案」、「寫成 .md」、「存成筆記」或類似需求，建立或更新 `.md` 檔案。
- 若使用者要產生檔案但沒有指定路徑，將 `.md` 檔案建立在 `C:\Users\User\Desktop\資訊業筆記`。
- 檔名應根據文章主題產生清楚的中文名稱，例如 `公開金鑰加密如何運作.md`。
- 若目標資料夾已有同名檔案，先詢問是否覆蓋，或使用更明確的檔名避免覆蓋。
- 寫入檔案時使用 UTF-8；讀取既有檔案時也優先用 UTF-8。若看到中文亂碼，先確認編碼，不要基於亂碼內容直接改寫。
- 修正既有 Markdown 時，應原地更新既有章節結構；除非使用者要求，否則不要另外產生「補充版」、「修正版」或「附錄」取代原本內容。

## 語氣與深度

- 使用繁體中文。
- 檔案內容與 skill 內容一律使用 UTF-8 中文處理。
- 最終內容使用 Markdown 格式輸出。
- 語氣要像在教一位正在學工程概念的 junior developer。
- 不要只說「A 是 B」，要補上「為什麼需要 A」與「沒有 A 會怎樣」。
- 不要過度學術化；先建立直覺，再補正式詞彙。
- 對 coding 人員要有實作價值：包含命名、角色分工、使用時機、錯誤用法與修正方向。
- 若文章本身很長，先整理主幹，再補必要細節。
- 若文章內容不完整或推論來自補充知識，要明確說「根據來源內容」或「延伸理解」。

## 品質檢查

送出前確認：

- 有附來源連結。
- 有清楚說明文章主旨。
- 有說明為什麼需要該概念。
- 有抓出真正重點，而不是逐段翻譯。
- 每篇文章都有直觀例子。
- 若主題需要讀者動手操作，已啟用實作教材模式，而不是只列摘要或大綱。
- 每個重要章節都有說明「學完能做到什麼」或等價的學習成果。
- 每個實作範例都有任務情境、操作前檢查、Step-by-step、預期結果、驗證方式與失敗排查方向。
- 每個技術實作範例都有「範例範圍地圖」或等價說明，列出相關檔案、元件、設定、指令、UI 介面、資料表、API endpoint 或外部服務。
- 沒有只給單一孤立片段。若範例需要多個部分才能運作，已補齊資料 / 設定 / 流程邏輯 / 入口點 / 使用端 / 執行方式 / 驗證方式。
- 每篇文章都有自己的「定義名稱對照表」，尤其是設計模式、架構、API、資安與流程型文章。
- 定義名稱對照表至少包含 `角色`、`文章中的名稱`、`功能 / 責任`。
- 每篇技術文章都有 C# 或該知識點最合適形式的可練習範例。
- 已依照範例形式選擇規則判斷：能自然用 C# 就用 C#；不能自然用 C# 時，使用該主題原生語法、命令、設定、操作流程或驗證方式。
- 沒有為了滿足 C# 而硬塞與主題不自然的 C# 範例。
- 程式碼中的重要 interface、class、method 註解有對應「定義名稱對照表」中的角色與文章名稱。
- C# 範例中的註解有說明範例用途、主要參數 / 輸入資料、回傳結果或副作用。
- C# 範例除了角色類別，也有使用端 / 呼叫端的實際操作方式，例如 client code、service 呼叫、API endpoint、handler 流程或測試情境。
- 使用端範例有結合工作場景，能看出輸入來源、呼叫流程、輸出或副作用。
- 若主題是 framework 或應用程式流程，已說明 framework 如何找到、建立或呼叫範例中的程式，例如 route、DI、middleware、event handler、job trigger、command entrypoint、設定載入或 UI 操作。
- 若主題是 MVC / Web app，沒有只貼 Controller、View、Model 或 Service 單一區塊；已補齊最小可理解組合，例如 Model / ViewModel、Service 或流程邏輯、Controller / handler、View / response、Program.cs / route / DI 設定與使用端流程。

- 若主題是資料庫，沒有只貼 SQL / Entity；已補資料表或 Entity、測試資料、查詢或 migration、應用程式呼叫方式、預期結果與資料異動風險。
- 若主題是 CLI / DevOps / 雲端，沒有只貼單一命令；已補工作目錄、前置條件、命令順序、預期輸出、驗證方式、失敗排查與清理或成本提醒。
- 若主題是設定檔，沒有只貼設定片段；已補放置路徑、讀取者、環境差異、機密處理、如何套用與如何驗證生效。
- C# 操作情境盡量貼近真實工程需求，不只是抽象玩具例子。
- 非 C# 範例有說明主要輸入 / 設定、預期輸出 / 畫面 / 副作用、如何驗證成功，以及失敗時先查哪裡。
- CLI、系統管理或 DevOps 範例有標註命令是否會修改系統，危險命令有練習邊界與安全提醒。
